# 下一批难题执行方案

**当前决定：旧三题停止扩张；先验证 hard3 的难度机制，再制作最多三道新原型。**

本方案交付的是执行顺序、实验矩阵、验收标准和记录模板，尚未创建新题或启动模型运行。历史研究见 `reports/workflow_hard3_review_20260912/ANALYSIS.md`。执行者可以是你本人或你委托的编码 agent；每一阶段都先交付文件，再判断能否进入下一阶段。

执行入口：[所需输入与目录](INPUTS.md) → [服务器命令](SERVER_RUNBOOK.md) → [分阶段委托指令](HANDOFF_PROMPTS.md)。[实验矩阵](experiment_matrix.json) 中的 14 项都是计划项，尚无题包或模型成绩；阶段结论填写 [决策模板](templates/stage_decision.md)。

## 一、最终想得到什么

得到一批实际有用、来源可追溯、题面充分、可离线提取的新任务；在固定 Flash 模型/运行条件下，**功能 pass@1 的设计目标为 25%–45%**。

这不是首批三题的验收比例，也不承诺用 3/6 次实验估计最终 50 题的通过率。模型低分只是难度证据，不能证明题目有效。

保持这些规则：

- 功能通过仍为 build ∧ public ∧ hidden ∧ isolation；不加入复制率或 LOC 惩罚。
- 代码复用合法。整包改名加薄适配就通过的候选，退出“功能 hard”选题池，但其结果仍是通过。
- 上游已有能力必须占核心；不把从头实现的新系统包装成提取任务。
- 差异来自真实消费者的独立接口/状态/依赖边界，不能为了难度任意反转上游行为。
- 旧三题、Python-150、Hard-50、已发布 freeze 和 Flash 157/200 全部保留。
- 本方案是看过已有结果后的前瞻方案，不声称对历史实验做了预注册。新内容只在封存后运行。

## 三、P0：先修实验可比性

负责人先完成以下工作，不要直接复制上一轮命令开跑：

1. 在服务器新建独立研究工作目录/checkout，保留现有主榜目录。记录 harness Git commit 和未提交补丁的 hash。不要将密钥放入任务、镜像构建上下文、归档或报告。
2. 固定 OpenHands 版本、agent/eval 镜像 ID、Python 版本、依赖 wheel 和 profile 内容 hash。历史不同 Python/freeze 的运行仅作背景；P2 对照各版本必须使用相同环境。若某旧题无法在选定 Python 下通过 oracle，先处理兼容性或排除该案例，不能记为模型失败。
3. 使用明确的 Flash API model id，并保存服务返回 model/system_fingerprint（若提供）、时间和 endpoint。别名不能证明服务端模型未更新；连续实验尽量在同一短时间窗口完成，跨版本变化就拆批。
4. 默认沿用研究中的 Main 条件：OpenHands、Full-Repository、No-Hint、standard prompt、evaluator tests 不可见、120 steps、3600 秒、128K context profile（131072 tokens，预留 8192）。**这次不另加本机临时运行器的 1M/2M 总 token 限制**，否则不再是同一预算设置。
5. 修复或核实上下文限制：请求输入应在 profile 限额内。canary 必须能验证接近上限时的压缩/截断行为；仅运行一条小请求不能证明限制有效。无法审计或仍超限，先停模型实验。
6. 为研究题建立专用 source registry，完整源码归档与 task ID 一一映射到 snapshot。运行后 `source`、snapshot ID、tree digest 不能像上次一样为空。
7. 建立专用参考计量注册或确保 harness 能解析研究参考解；核对 `reference_loc` 真正来自该版本参考，而不是 null。参考不一定最小，报告注明。SQLGlot 整包参考不能作为高质量最小闭包标准。
8. canary 选旧 pip/dbt/SQLGlot 三个对照，仅用于验证环境、配置与记录。它们不加入新题统计。以 1 次起步，最多 3 次；参考解用 Docker 先过一遍。

交付 `environment.json`。另保存 `canary/*/run.json`、`eval/result.json`、profile hash、source/输入锁验证、上下文审计。**P0 必须先过，否则后面的模型结果不具备可比性。**

## 四、P1：先审六个案例，不先重写题

| 案例 | 要核对的事实 | 需要回答的问题 |
|---|---|---|
| tenacity | idle_for 与 before_sleep 的先后、停止边界、异常与结果回调 | 回调观测差异是否有消费者理由？只是改一行就能解决，还是影响状态流程？ |
| glom | Coalesce 列表接口、嵌套 spec、默认值传播 | 适配是否停在最外层？内部递归仍按原生参数理解吗？ |
| alembic | 版本边/依赖边/合并点/分支标签与查询输出 | 失败来自真实图角色组合，还是输出类型没有充分说明？ |
| requests-cache | 多入口参数绑定、头/URL/body 的归一化与脱敏 | 参数和返回值是否明确？规则在不同入口是否一致？ |
| pluggy | call_historic、add_hookwrapper 的接口声明和调用方式 | 是否主要由未声明 API/参数次序制造失败？ |
| responses | 未命中的 call_history、once 消耗与 reset | 是否明确说明失败尝试也记历史？ |

每个填写 `templates/case_card.json`。必须同时引用：当时 agent 可见 TASK、匹配版本的测试、pinned source、实际 submission、失败断言。**不能把当前题面与旧 run 的失败日志混用。**

记录每个异常点：

- `explicit_adaptation`：目标清楚声明与原生不同的协议；
- `semantic_integration`：目标继承上游语义，但提取遗漏跨接口/状态行为；
- `contract_risk`：不能从题面或已声明协议确定测试要求；
- `infrastructure`：环境、依赖、版本、上下文等问题；
- `undetermined`：证据不足。

这些是本研究工作标签，不冒充论文 F3 人工标注。不要根据“模型失败了”反推某类标签。至少让一个未编写 oracle/测试的人或独立 reviewer 审查，标明 reviewer 类型；AI 审查不能标成人工审查。

P1 输出一页结论：哪些机制还值得测，哪些案例只能作为规格风险对照。若全部解释为缺陷或简单改名差异，结束 P2 扩展，直接回到来源需求研究。

## 五、P2：机制对照怎么做

使用 `experiment_matrix.json` 的 14 个预留版本，均在独立 staging 目录，原题不变：

- **O：原版研究副本**。恢复该案例历史 run 对应的完整输入；仅改研究 task ID、必要 provenance 和派生 hash，API/行为/测试/参考/依赖内容保持一致。恢复不了就记 missing，不拿其他版本代替。
- **C：明确契约版本**。把消费者需要的接口、默认值、异常、回调时序和输出语义完整声明。已有清楚的范围不额外加需求。若原版欠定，必须说明 C 选择了什么解释；不能未经审查声称“范围没变”。先封存内容，再运行模型。
- **N：原生协议诊断版本**。只给 tenacity、glom 建立，将关键适配改为 pinned upstream 原生协议；必要时同步变更对应测试。它是不同任务范围的诊断对照，不是正式修复，也不与 O/C 的 pass 合并。

O/C/N 必须共享来源 commit、依赖环境、工具权限、预算与其他可保持相同的测试维度。为每条变更写 `variant_diff.md`，注明影响哪些断言。N 的测试只改比较所需部分，不能删除难例来制造通过。

每个版本按创建/验证技能流程生成 `public_spec → TASK.md`，三次 Docker oracle 全过、输入稳定，并取得语义审查结论。对源码继承部分做上游差分；对适配差异用消费者契约和独立 oracle，不声称两者完全同源。

**首轮：14 个版本 × Flash 1 次 = 最多 14 次。**
运行顺序在封存前固定并交错 O/C/N，最大并发 2；不要总把一个版本放在一天最后。每个独立 run 使用新 workspace、输出目录和会话，不能沿用历史解或给定模型失败反馈。

**确认：只有 tenacity/glom 的 C/N 出现有价值差异时，才对相应 C/N 各增加 2 次独立运行，总增量最多 8 次。** 所有重复都保留，报告逐题序列如 `[pass, fail, fail]`，不取“至少成功一次”。O/C 如果暴露严重歧义，优先停止而不是追加确认。

| 观察 | 判读 | 后续动作 |
|---|---|---|
| O 失败、C 通过 | 旧表现可能受披露/歧义影响 | 不以该旧失败支撑难度；保留诊断 |
| C 失败、N 通过，且重复有一致趋势 | 适配可能增加了真实负担 | 审核消费者理由、最小修复和源码作用；作为新来源选题线索 |
| C、N 都通过 | 切片或适配对当前模型偏易 | 不扩此切片 |
| C、N 都失败 | 不能证明适配起作用 | 分析共同失败、定位负担、模型运行/题面问题 |
| 参考失败或错误暴露未声明要求 | 无法有效比较 | 停止该版本，另建修订，旧结果保留 |

**进入 P3 的工作门槛**：至少一个经过审查的实际需求机制，有可复用上游核心，至少一个有效提交失败可定位到明确的语义义务；如果引用 C/N 对照作为证据，还应有 N 可行的观察。小样本只作为继续研究的理由，不作为因果或通过率证明。

## 六、P3：新题该怎么选和交付

先找最多 6 个来源候选，每个最多花一个工作日做可行性审查；没有来源证据就淘汰。这个时间是限制研究投入，不是对模型施加时间压力。
最多选 3 个不同代码闭包物化；优先不同仓库。同一库的不同 wrapper 不充数；先检查现有 150/Hard-50/退役 External-50 的仓库和闭包重叠。

优先方向：

1. **可嵌入的作业重试会话**：显式执行器/时钟，结果和异常策略、停止、取消、回调观测、会话隔离。上游没有取消或会话生命周期实现，就删除该方向或换来源，不能凭空增加。
2. **显式提供者的插件调度**：替换宿主发现/配置系统，保留包装器、临时注册、错误展开、清理和实例隔离。不能只做一个字典注册器。
3. **本地增量配置/依赖规划**：把真实宿主的配置/图状态边界剥离，验证覆盖、依赖角色、更新后的失效与失败后状态。上游不保证原子性，题目不能假称继承原子性。

每个候选先写一段可以由真实调用者使用的 consumer example，说明谁调用、输入来自哪里、返回值决定什么、为什么不能直接装原库。若答案只有“benchmark 不让装”，实际用途论证不充分。

使用 `templates/candidate_card.json`。题包必须交付：

- pinned source/license、完整源码归档、专用 registry、重叠检查；
- `public_spec`、生成 TASK、API 全表、输入输出/错误/状态/依赖契约；
- public/hidden 测试和逐断言到条款的映射，维护者层面的序列覆盖说明；
- reference、来源继承与适配差异说明、独立 oracle、三轮 Docker 验证；
- 三个实做基线和提交/日志：整包改名加薄适配、核心搬运加朴素宿主替代、独立浅实现；
- 非最小参考说明/闭包审计、完整输入锁与变更记录。

**测试选择依据是可观察义务，不是达到多少个测试。** 例如“注册→临时覆盖→回调抛错→清理→再次调用”的一次序列，比复制几十个常规输入更能检查协议闭合；但序列每一步都必须属于公开契约和实际使用场景。

淘汰条件：

- 单个已独立封装的成熟入口，加无状态薄 wrapper 即可完成；
- 全包/相关子包在合法运行边界下轻松通过所有测试；
- 所谓难点只是未声明 API、反常默认值、任意参数位置或实现细节；
- 核心来自新写的业务逻辑，上游没有对应能力；
- 参考无法离线运行、依赖服务/宿主偶然状态，或与现有题实质重复。

基线失败本身不是过关：要确认它实做了目标、不是因语法/导入错误失败。给机械搬运基线允许合理的 import/namespace 修正和声明边界的薄适配，并记录修改；不能故意做坏它。

## 七、P4：三个原型如何决定去留

题包与模型运行配置封存后，最多 3 题各跑 Flash 2 次独立尝试，共最多 6 次。有效版本再跑第二模型各 1 次，最多 3 次。第二模型也用相同信息边界和可审计预算，记录不同的模型配置。

- Flash 两次都通过：在本轮功能 hard 目标下停止该题，留作对照；不是宣称它永远简单。
- 一过一败：继续候选；必须解释有效失败与正确路径，不能只看 50%。
- 两次都败：仅标“潜在难题”。若因为缺陷/环境则不能保留；若仅该 Flash 的模式性偏差，第二模型结果帮助判断。第二模型也失败不自动淘汰，但需要更强的可行解和公平性证据。
- 有规格缺陷：新版本修复后重新封存，分开记录；不继承旧版难度数字。
- 三个全部容易或全部无效：停止扩题，回到 P1/P3；不靠增补同类 hidden 压分。

**P4 结束不产生“新集达到 25%–45%”的结论。** 最多 6 次 Flash 运行不足以估计目标带。

## 八、何时才能扩到 12 或 50

P4 后单独作决策：至少两个来源/闭包不同的候选具备有效、可解释的困难，才值得提出下一轮 8–12 候选的预算和范围；达不到则继续寻找机制，不凑数量。

扩大时先封存候选池和选择规则，保留通过/失败/淘汰的全部任务。用开发筛查选题后，固定成员与题包，使用新会话进行独立确认，报告整个筛选过程。
确认阶段不能再根据结果删除通过题以挤进目标带；若不达标，报告未达标并在下一版本重新研究。

统计同时列出：任务数、每题尝试数、每轮 pass@1、逐题成功次数、失败类型、环境异常数量和区间。重复同一题不等于增加独立题数；聚合区间应考虑任务聚类。
若最终是 50 题 × 每题一次，25%–45% 对应 13–22 道功能通过（离散范围为 26%–44%）；这一观测范围也不保证总体真值位于该带。不要给“必达标”的承诺。

## 九、你现在就可以做的三件事

1. 把本目录同步到服务器，按 `SERVER_RUNBOOK.md` 完成 P0，交付 `environment.json` 和一份 canary 报告。
2. 按 `experiment_matrix.json` 先做六张案例卡，**先别批量建 14 个版本**。完成规格审查后再决定哪些版本具备构造条件。
3. 通过审查的版本按矩阵物化、oracle 验证、封存，然后才跑模型。每阶段把报告交回来，按上述门槛决定是否继续。

可复制的委托指令在 `HANDOFF_PROMPTS.md`。字段模板都用 null/空数组表示未完成，不能把模板存在当成通过证据。

34 次是模型生成运行数量上限，不是 API 请求数或费用上限；一次 agent 运行可能包含很多 API 请求。先用 P0 实测 token/费用记录估算后续批次成本，进入下一阶段前确认资源安排，不能将上一轮三题的耗时直接外推。
