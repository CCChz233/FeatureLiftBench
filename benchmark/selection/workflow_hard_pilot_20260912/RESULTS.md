# 新难题原型：当前交付与判定

这批任务沿用 Python-150 的完整仓库、无入口提示、离线独立提取协议。
难度来自实际工作流中多阶段语义的组合，而不是扩大仓库、增加干扰文件、
限制时间或隐藏题面要求。当前交付 **3 个可执行原型，其中 2 个进入待校准池，
1 个保留作反例对照**。尚未完成 12 题或 50 题正式新集。

## 已实现的题

| 上游与任务 | 实际用途 | 关键提取行为 | 当前判定 |
|---|---|---|---|
| pip / `choose_distribution` | 离线镜像或隔离部署环境选择安装制品 | 目标解释器、wheel 标签、Requires-Python、候选集哈希过滤、预发布与撤回版本、排序偏好的组合 | `fix_required`：等待隔离与强模型校准 |
| dbt-core / `select_nodes` | 从已有 manifest 为 CI 选择模型及相关测试 | 图遍历、深度、并交差、四种间接选择模式、组合后的待定测试依赖、最终类型过滤 | `fix_required`：等待隔离与强模型校准 |
| SQLGlot / `trace_column` | 无数据库连接的列级数据影响分析 | 别名、JOIN、嵌套作用域、CTE、UNION、schema 与 source 展开 | 当前方案 `reject` 难题池：保留整包复制对照 |

所有包位于 `benchmark/staging/<task_id>/`，生命周期仍是
`materialized_candidate`。包含生成的 TASK.md、public_spec、公开/隐藏测试、
requirements.lock、禁用导入规则、私有来源说明、参考解和简单基线。
metadata 的 `hard` 是构造目标；`difficulty_evidence.status=uncalibrated`
明确表示没有得到实测难度认证。

## 已取得的证据

固定上游：pip 25.2 / `2e05cae3da2cfafa6dce58167a25b7dba4bc2a33`；
dbt-core v1.10.11 / `7d7d64ed6724f77d25c7e75d14751b9515a474ef`；
SQLGlot v27.14.0 / `cce19bbccf61198263208cf07f2fd3aed0d8217b`。
完整 Git blob 归档保留原始文件模式，含许可证；3 个 archive SHA-256 和
tree SHA-256 均通过验证。注册表为独立的
`benchmark/sources/workflow_hard_pilot_registry.json`，没有改写主榜注册表。

129 个输入场景先在固定上游模块上生成结果，再与提取的参考解比较。
引用上游模块时检查了实际导入位置；dbt 的 plain-record 适配边界有显式说明。
此验证独立于提取后的引擎，但共享公开输入适配层，因此不能替代独立人工规格审查。

| 原型 | 场景数 | 公开测试 | 隐藏测试 | 参考解三轮 | 简单基线单轮 |
|---|---:|---:|---:|---|---|
| pip | 35 | 4 | 33 | 每轮 37/37 | 公开 2/4、隐藏 19/33 |
| dbt-core | 72 | 4 | 70 | 每轮 74/74 | 公开 4/4、隐藏 62/70 |
| SQLGlot | 22 | 4 | 20 | 每轮 24/24 | 整包改名复制 24/24 |

测试数包含每个 tier 的一个重复调用检查，所以总数为 135，三轮共 405 次
pytest 测试通过；这不是 405 个独立场景，也不是模型通过率。
两个 shallow_policy 基线是有用但不完整的独立实现，没有空函数或人为填充。
dbt 基线公开测试全过而隐藏组合测试失败，说明这些场景能检出真实的组合语义遗漏；
它仍通过大多数隐藏测试，不能据此断言强模型会失败。

本地参考规模：pip 662 行/2 Python 文件，dbt 482 行/2 文件，
SQLGlot 46,426 行/77 文件。口径为非空、非纯注释行，是开发测量而非正式
compactness 指标。前两者为上游定义的定向提取；均未证明最小闭包。
SQLGlot 参考本身是保守的整包复制，不能拿它作紧凑性分母来证明提取质量。
它还与退役 External-50 有仓库重叠，不能计入 source-disjoint 新题。

最新完整运行：
`experiments/validation/workflow_hard_pilot/20260912T101718Z/summary.json`。
3 个任务的 `validate_task` 均通过，注册表 schema 无错误，静态禁止导入扫描无命中。
每轮启动新进程、只复制 submission 与 tests，并阻止上游导入、源目录访问和常规网络调用。
这属于开发级检查，不等价于 OS/Docker 隔离；本地虚拟环境含额外上游依赖。

## 构造过程中保留的失败

初次参考回放发现 dbt 适配 mixin 的 MRO 错误、SQLGlot 命名空间改写错误，
随后修复。跨进程重复运行又发现上游 downstream 来自无序集合，造成 SQL
血缘树结果顺序不稳定。修订 2 将公开适配契约明确为递归 JSON 排序，
保留所有节点和重复分支；已有上游期望仅做同样的排序转换。
排序后没有重新运行上游 probe，证据中明确记录该事实。
所有旧失败日志保留在同一 validation 根目录，未被覆盖；修改前没有模型校准运行。

## 下一道门槛

1. Linux Docker 中用白名单依赖复验参考解与隔离。
2. 独立审查题面与上游语义、全部隐藏场景、公平性和来源/闭包重叠。
3. 锁定输入后，使用既有 Hard-50 对比实验的相同模型配置与预算，至少两种强模型、
   每题至少 3 次独立运行。完整保留失败与基础设施错误，不用重试后的最好成绩替代 pass@1。
4. 同时审查失败是否来自定位、语义闭合、宿主解耦或基础设施；通过率低但题面有缺陷的题淘汰。
5. 区分功能通过与代码提取质量。若强模型普遍通过或整包复制捷径成立，淘汰候选或重新选切片；
   不在看到模型结果后给同一版本暗加隐藏要求。
6. 由这些证据决定是否扩到 12 题，再决定 50 题；新增仓库和切片须重复同样流程。

当前机器无运行中的 Docker Linux 引擎，无项目模型凭据配置；依赖 wheel 缓存也尚不完整。
Windows CLI 另有 `fcntl` 导入限制，本地使用直接 harness API 验证。
因此尚无 Docker 通过、强模型难度校准、完整闭包/泄漏审计或正式晋升证据。
题库输入包和服务器命令见 `SERVER.md`。Python-150、Hard-50、已有 freeze 和论文结果未改动。
