# FeatureLiftBench Benchmark Repair Protocol

> **Status: current candidate protocol · Version: v1 · Adopted: 2026-09-03**
>
> This protocol governs repairs between immutable benchmark freezes. It does
> not authorize edits to an already published freeze and does not make model
> scores an admissible reason for changing a task.

## 1. Purpose

FeatureLiftBench permits a task repair only when an existing, versioned
benchmark rule identifies a validity defect and the repair preserves the
task's intended functional scope. The repair process must distinguish three
questions:

1. Did the previous task violate a written benchmark rule?
2. Is the proposed change the smallest change that removes that violation?
3. Does the repaired task retain a valid, deterministic and isolated oracle?

The process is **protocol-governed post-hoc benchmark remediation**. It must not
be described as preregistration when the protocol was written after exploratory
model runs.

## 2. Non-negotiable invariants

A repair is admissible only when all of the following hold:

```text
AdmissibleRepair =
    ConfirmedRuleTrigger
    AND EvidenceBeforePatch
    AND MinimalChange
    AND NoModelScoreCriterion
    AND ContractOrProvenanceJustification
    AND OracleAndIsolationPass
    AND VersionSeparation
```

### 2.1 Confirmed rule trigger

Every repair must name a rule in
[`TASK_DESIGN_RULES.md`](TASK_DESIGN_RULES.md) or
[`BENCHMARK_VALIDATION_GATE.md`](BENCHMARK_VALIDATION_GATE.md). A mechanical
finding that requires adjudication is not sufficient until its adjudication is
recorded. An advisory finding may justify maintenance, but it must remain
identified as advisory rather than being rewritten as a blocking violation.

### 2.2 Evidence before patch

The ledger must retain the pre-repair task identity, failing check, concrete
test or source symbol, adjudication, rationale and evidence path. A repair with
no recoverable pre-repair evidence is rejected.

### 2.3 Minimal change

The patch must touch only the defective layer:

| Repair class | Allowed change | Disallowed change |
| --- | --- | --- |
| C1 surface disclosure | Add an already exercised, in-scope API member to `required_api`; regenerate derived TASK/mapping/surface checks | Delete the Hidden obligation merely to clear C1; add unrelated APIs or behavior |
| C2 provenance correction | Replace a dangling private source pointer with a real pinned-upstream symbol, or remove an unsupported pointer | Invent a resolvable but irrelevant symbol; expose the pointer in Main |
| C4 overlap removal | Replace the duplicate Hidden case with a distinct case entailed by the same published behavior | Add a new behavior, API, exception, environment assumption or difficulty target |

If the functional scope must change, the artifact is a newly designed task,
not a repair under this protocol.

### 2.4 Model-result independence

Pass rates, individual Agent failures and desired task difficulty are not
repair acceptance criteria. They may identify an area for audit, but the final
decision must be supported by a benchmark rule and contract/upstream evidence.
No post-repair score may be consulted before the repaired content is sealed.

### 2.5 Executable preservation evidence

The repaired task must pass:

- package and contract validation;
- API/behavior mapping checks;
- canonical source identity checks;
- reference public and Hidden evaluation;
- isolation checks;
- three deterministic Oracle repetitions with one stable fingerprint;
- leakage and public/Hidden overlap checks.

An Oracle pass establishes executability, not semantic fairness. C1/C2/C4
repairs additionally require the semantic review in Section 4.

### 2.6 Version separation

Repairs are never written back into the identity of an old result. A release
containing repairs requires a new candidate manifest and final freeze. Old
tasks, reports and model results remain attributable to the old freeze.

When suite membership is unchanged, the task-ID-set digest may remain stable.
Content changes are represented by per-task revisions and tree/spec hashes, the
candidate ID and the final freeze ID.

## 3. Required repair ledger

The machine-readable ledger is generated by
[`build_python200_prime_repair_ledger.py`](../scripts/build_python200_prime_repair_ledger.py)
and stored at
`artifacts/research_analysis/python200_prime/current_repair_ledger_v2.json`.

Each task record must include:

- pre- and post-repair input identities;
- triggering rule(s), severity and pre-repair evidence;
- the concrete C1 members, C2 pointers or C4 overlap evidence;
- whether Agent-visible content or evaluator content changed;
- the claimed semantic-scope effect;
- mechanical, Oracle/isolation, semantic-review and freeze status;
- hashes of all source evidence used to build the ledger.

The ledger uses `semantic_review_status: pending` until a separate reviewer
confirms that the repair stays within the original task scope. Mechanical gate
success must never silently upgrade this field.

## 4. Semantic review

For every changed task, the reviewer checks only admissible evidence:

- the public contract and generated TASK;
- the pinned upstream source, tests, documentation and examples;
- Hidden tests only to identify the evaluator observation, never as evidence
  that the observation is publicly recoverable.

The reviewer records one of:

| Verdict | Meaning |
| --- | --- |
| `scope_preserved` | The change discloses/corrects/diversifies an obligation already inside the original task scope |
| `scope_changed` | The repair changes the required functional slice; it must be redesigned or versioned as a new task |
| `insufficient_evidence` | Public and upstream evidence cannot establish the claim; release remains blocked |

For the Python-200-prime repair, all 38 changed tasks require this review. The
Flash-33 provenance slice should additionally reach dual-reviewer consensus,
and a stratified sample of mechanically clear tasks should be audited to
estimate false-negative risk. A claim that all 200 Hidden evaluators were
semantically reviewed requires reviewing all 200; sampling cannot support that
universal claim.

## 5. Release sequence

After all changed-task semantic reviews are closed:

1. rerun the 200-task benchmark gate against the final task trees;
2. require `200 meets_standard / 0 violates / 0 undetermined`;
3. generate and archive a new candidate manifest;
4. build candidate-labelled linux/amd64 Agent and evaluator images;
5. rerun the 200 x 3 Oracle/isolation gate on that evaluator image;
6. build an immutable final freeze;
7. publish the 200/0 analysis JSON (and archive the 168/32 predecessor).
   Experiment task files under `harness/config/experiments/` are hashed into
   the candidate; write the 200/0 lists **before** Step 3, not after.
8. only then run paper Main and ablation experiments.

Any content change after Step 3 invalidates the candidate and returns the
process to Step 1.

## 6. Paper reporting

Report the repair as a validity measurement, not as model improvement:

- before: 168/200 tasks met the blocking standard;
- findings: 33 confirmed blocking findings across 32 tasks, plus six C4
  advisory overlap findings;
- after mechanical remediation: 200/200 passed all nine implemented gate rows;
- semantic scope: report the completed review counts and unresolved cases;
- Oracle/freeze: report only evidence produced for the new candidate and image;
- Agent results: never move scores from the predecessor freeze to the repaired
  freeze.

The paper must disclose that the repair protocol is post-hoc, that semantic
entailment is not fully mechanizable, and whether review provenance is AI,
maintainer or independent human.

## 7. Rejection conditions

A proposed repair is rejected when it:

- lacks a rule-based pre-repair finding;
- is justified primarily by model performance;
- expands or narrows the task's functional scope;
- weakens Hidden tests solely to increase pass rate;
- introduces a source hint into Main;
- lacks pinned-upstream evidence for a semantic claim;
- fails reference, isolation or determinism validation;
- attempts to retain the old candidate/freeze identity.
