# FeatureLiftBench 论文进展汇报

> **日期：** 2026 年 8 月 31 日  
> **拟定方向：** Benchmark + Empirical Analysis

## 摘要

FeatureLiftBench 面向仓库级、行为保持的功能抽取任务：给定固定版本的完整真实仓库和公开行为契约，要求代码 Agent 在没有源码位置提示、没有评测测试和参考实现的条件下，交付可独立安装、行为完整且不依赖原仓库运行的功能包。该任务同时要求仓库理解、行为契约恢复、依赖与资源闭包、模块解耦以及实现紧凑性，区别于现有 benchmark 中常见的 issue repair、代码定位或从零生成任务。

该任务的现实意义在于评估 AI 生成代码进入实际使用之后的可演化性。随着 vibe coding 和自主代码 Agent 降低应用生成门槛，越来越多项目可能在“功能已经可用并经过测试”的情况下，其内部结构、设计理由和依赖边界并未被维护者充分掌握。当这些项目需要模块化重构、能力复用、依赖缩减、所有权移交或离线部署时，关键问题不再是能否重新生成一份代码，而是能否从既有系统中识别真实行为边界，在不破坏已验证功能的前提下将目标能力安全地抽取出来。FeatureLiftBench 因而衡量的是 AI 辅助开发生命周期中“生成之后”的维护与重构能力。

目前，benchmark 的任务定义、评测协议和 Python 主套件已基本形成。冻结 Python-150 已获得四个模型配置的完整探索性结果，Functional Pass@1 从 18.0% 到 66.0% 不等，表明该任务具有明确的能力区分度。任务级分析进一步显示，即使两个模型具有相同总通过率，其成功任务集合也可能存在显著差异。现有结果还表明，模型间差距主要出现在 Public 和 Hidden 行为检查，而非 Build 或 Isolation。

在方法方面，已围绕自生成测试、契约检查、characterization harness、差分修复、checkpoint、预算控制、上下文管理和自动 prompt 优化开展多组实验。迄今尚未观察到相对于无帽 Main 协议稳定、可复现的 Functional Pass 提升。相关负结果共同指向一个较为一致的现象：当前 Agent 通常能够定位并重建目标功能的主体实现，但仍难以在 test-blind 条件下完整闭合公开契约中的边界行为、异常语义、状态转换、资源依赖和必需 API 表面。

基于上述进展，论文拟由“Benchmark + 新方法”调整为“Benchmark + 实证分析”。论文的主要贡献将集中于新任务定义、严格评测基准、正确性与紧凑性的双轴评价，以及对模型能力差异、契约闭合失败、Public/Hidden 信息边界和方法负结果的系统分析。当前最关键的后续工作是完成合格的 Python-200$'$ 跨模型主表、Hidden 公平性审计和必要的稳健性实验。

## 1. 研究问题与任务定义

### 1.1 任务定义

现有代码 Agent benchmark 主要覆盖两类任务：一类是根据 issue 描述修复既有仓库，另一类是根据自然语言需求生成新的实现。FeatureLiftBench 研究的是不同的问题：从真实仓库中识别并抽取指定功能，将其重构为独立、可复用的功能包，同时保持公开契约要求的可观察行为。

所有任务共享一个统一前提：Agent 被清楚告知目标功能及其任务范围，并必须将其视为一个完整的 task-scoped module，而不是若干孤立的行为示例。Agent 需要主动检查完整上游仓库中的源码、测试、文档、示例、配置和资源，自行发现实现位置，恢复范围内的具体行为契约、边界与异常语义、状态行为以及传递依赖闭包。TASK 中的 Target API、Required Behavior、Constraints 和 Exclusions 穷尽地划定评测范围；范围内全部义务均为强制，但不要求复刻范围外的整个上游项目，Hidden 也不得越过该公开范围增加新义务。

在 Official Main 协议中，Agent 可以获得：

- 固定 commit 的完整上游仓库；
- 目标包的 Required API；
- 主路径、边界行为、异常语义及排除项等公开契约；
- 允许依赖和禁止依赖信息。

Agent 不可获得：

- 目标源码位置或符号提示；
- benchmark 的 Public / Hidden 测试；
- evaluator、参考实现和参考 footprint；
- 基于正式评测结果生成的修复反馈。

最终交付物为独立的 `featurelifted` 包。该包在运行时不得导入原仓库、读取原仓库文件或依赖外部服务。

主评价指标为单次运行的 Functional Pass@1：

\[
\text{Functional Pass}
= \text{Build} \land \text{Public} \land \text{Hidden} \land \text{Isolation}.
\]

- **Build** 检查提交是否可以安装和导入；
- **Public** 检查公开契约中的主要功能路径；
- **Hidden** 检查同一公开契约中的边界、异常类型、状态转换、必需导出和保真要求，不引入新的私有条款；
- **Isolation** 检查提交是否真正脱离原仓库运行。

实现紧凑性使用 Reference-Relative Extraction Size（RRES）和启发式复制比例等指标单独评价，并且仅在 Functionally passing 的提交上计算。正确性与紧凑性不合并为单一总分，以避免大范围复制但功能正确的提交掩盖抽取质量问题。

### 1.2 为什么这一问题在 AI 辅助开发时代更加重要

代码 Agent 正在将软件开发从“人直接编写每一段实现”转向“人描述意图、配置环境并验证结果”。OpenAI 在 2026 年公开披露 Codex 每周用户已超过 500 万，其中约 20% 为非开发者；其内部 agent-first 工程案例还报告了在数周内形成百万行级代码库的实践。这些材料不能直接证明生成代码的长期质量，但说明代码生产正在更大规模地被委托给 Agent，维护者与具体实现之间的知识距离可能随之扩大（[Codex 使用情况](https://openai.com/index/codex-for-every-role-tool-workflow/)，[agent-first 工程案例](https://openai.com/index/harness-engineering/)）。

在这种开发模式下，“功能可运行”与“系统可演化”之间可能出现新的缺口。近期一项基于 6,275 个 GitHub 仓库和 304,362 个经验证 AI-authored commits 的预印本研究发现，不同代码 Agent 产生的提交中均有超过 15% 引入至少一个静态分析问题，且被跟踪问题的 24.2% 在仓库最新版本中仍然存在。另一项关于 vibe coding 的实践研究将这种现象概括为 flow-debt trade-off：快速生成带来即时开发流畅性，同时可能积累架构不一致、缺少设计依据和更高维护成本（[AI 生成代码技术债研究](https://arxiv.org/abs/2603.28592)，[Vibe Coding in Practice](https://arxiv.org/abs/2512.11922)）。上述研究仍有数据识别和外部有效性限制，但共同指出：随着生成成本下降，理解、验证、重构和治理既有代码的重要性不会同步下降。

FeatureLiftBench 所研究的功能抽取正是这一生命周期问题的一个可控切面。它要求 Agent 面对一个已经存在并具有真实依赖关系的系统，不依赖源码位置提示重新识别目标能力的实现边界，恢复公开契约所要求的行为，收集传递依赖与资源，并将其重构为可独立验证的包。该任务可以被理解为对 **maintenance after generation** 能力的评测：Agent 不仅要会增加代码，还要能够安全地减少、拆分和重新组织代码。

### 1.3 现实应用场景及其与 Benchmark 设计的对应关系

| 现实场景 | 现实中的核心问题 | FeatureLiftBench 对应能力 |
| --- | --- | --- |
| AI / vibe-coded 项目的后续重构 | 项目已经能够运行并经过用户验证，但维护者不完全理解内部实现；新增需求开始受到耦合、重复和隐式依赖阻碍 | 从完整陌生仓库中定位能力，在没有源码提示的条件下恢复行为边界并完成模块化 |
| 单体系统拆分与服务化改造 | 目标能力与配置、registry、状态、资源文件和框架生命周期纠缠，直接搬移容易产生隐蔽回归 | Public / Hidden 行为检查、传递依赖闭包、资源保真和 Isolation 共同验证拆分完整性 |
| 遗留系统现代化与所有权移交 | 原作者离开、文档不完整或设计理由丢失，但已有行为仍被业务依赖 | 以公开契约而非内部实现作为迁移边界，检验 Agent 对陌生代码和隐式契约的恢复能力 |
| 跨产品复用与内部公共库建设 | 多个项目重复实现相似能力，需要抽取为共享包，同时避免把整个上游系统一并复制 | 独立安装、禁止运行时依赖原仓库，并以 RRES、复制比例和依赖 footprint 评价抽取质量 |
| 依赖、许可证与软件供应链治理 | 组织只需要大型第三方项目中的局部能力，希望减少高风险或不再维护的依赖，并识别大范围复制 | allowed / forbidden dependencies、Isolation、复制比例和依赖 footprint 提供可审计证据；当前 benchmark 只测量相关技术能力，不直接判定许可证合规 |
| 边缘、离线和隐私敏感环境部署 | 原功能依赖大型框架、网络服务或仓库内资源，目标环境只允许部署最小核心能力 | 禁止外部服务和原仓库运行时依赖，验证必要资源与行为闭包是否能够独立存在 |

这些场景的共同结构是：已有系统中的目标行为具有现实价值，但原实现的组织方式、依赖范围或所有权结构不再适合下一阶段使用。人工完成此类重构通常需要代码考古、契约恢复、依赖追踪、回归验证和反复清理。若代码 Agent 能够可靠完成这一过程，它不仅可以提高一次性代码生成速度，还能够降低 AI 生成项目和传统遗留项目的长期演化成本。

因此，FeatureLiftBench 的实际价值可以概括为三个层次：

1. **对模型研发者：** 判断 Agent 是否具备从“生成局部实现”走向“维护和重构完整系统”所需的仓库理解与契约推理能力；
2. **对工具与平台开发者：** 评价代码 Agent 是否适合模块抽取、单体拆分、依赖瘦身和遗留系统现代化等真实工作流，并定位其失败发生在构建、主路径、边界行为还是隔离阶段；
3. **对软件使用者与组织：** 为是否可以将高风险重构任务交给 Agent 提供可复现证据，而不是仅依据代码生成演示或单元测试通过情况作出判断。

需要说明的是，本 benchmark 并不声称功能抽取可以代表全部软件维护，也不直接测量架构设计质量、长期演化成本或许可证合规。它选择了一个边界清晰、可以自动评测、同时组合了程序理解、行为保持、解耦和最小化要求的任务，用于检验当前 Agent 是否具备从“能生成”迈向“能治理和演化既有代码”的基础能力。

## 2. Benchmark 构成与当前状态

### 2.1 Python 主套件

| 范围 | 规模 | 论文中的作用 |
| --- | ---: | --- |
| 冻结 Python-150 | 150 题 / 127 仓 | 已获得四模型探索性结果 |
| Hard-50 | 50 题 / 50 个不重叠仓库 | 难度校准和复杂闭包任务 |
| Python-200$'$ | 200 题 / 176 仓 | 计划中的论文主套件 |
| External-50 | 50 题 / 50 仓 | 历史旁路分析，不进入新主表 |

早期版本使用“Python-150 + External-50”的 200 题组合。后续审计发现，External-50 对强模型整体偏易，并且存在较明显的 copy-heavy 通过方式。因此，当前主套件改为“冻结 Python-150 + Hard-50”，记为 Python-200$'$。Hard-50 的独立 Flash 设计校准结果为 29/50，用于提高主套件的有效难度和行为闭包复杂度。

每道任务还从三个维度进行标注：功能族、纠缠机制和抽取方式（Direct、Adapted、Composite）。这些标签仅用于题集平衡和分析，不对 Agent 可见。由于任务并非随机抽样，部分标签采用 AI 辅助，相关切片结果应视为描述性证据，而非任务属性对成功率的因果估计。

### 2.2 Python-200$'$ 主表尚未达到论文资格要求

2026 年 8 月 29 日收到的 DeepSeek V4 Flash 结果包记录了 132/200 的 Functional Pass。然而，该数字不能作为论文主表结果，原因如下：

- 17 道任务在 Agent 启动前被 freeze 一致性检查阻断；
- 16 道任务受到评测端离线依赖不足影响；
- 59 道任务触发 context-window 资格审计；
- 上述问题去重后形成 84 道严格替换或重跑任务；
- 替换运行与原结果包之间仍存在 agent / evaluator 镜像身份不一致问题。

因此，132/200 仅能作为 received-suite audit headline，不应写入摘要、最终 leaderboard 或跨模型结论。论文主表需要在统一的任务冻结、上下文策略和镜像身份下重新形成。

## 3. 冻结 Python-150 的探索性结果

冻结 Python-150 是目前证据最完整的跨模型比较。四个模型配置使用同一 OpenHands Main 协议和同一批 150 道任务。

### 3.1 总体结果具有清晰的模型区分度

| 模型配置 | Functional Pass@1 | Wilson 95% 置信区间 | Build | Public | Hidden | Isolation |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| DeepSeek V4 Flash | **99/150（66.0%）** | [58.1%, 73.1%] | 144 | 120 | 106 | 144 |
| Qwen3.5 122B | **59/150（39.3%）** | [31.9%, 47.3%] | 150 | 90 | 69 | 148 |
| Qwen3.6 35B | **59/150（39.3%）** | [31.9%, 47.3%] | 137 | 85 | 64 | 135 |
| GPT-OSS 120B | **27/150（18.0%）** | [12.7%, 24.9%] | 134 | 66 | 32 | 130 |

上述结果表明，FeatureLiftBench 能够区分不同模型配置的仓库级功能抽取能力。DeepSeek V4 Flash 的区间估计与两个 Qwen 配置不重叠，GPT-OSS 则进一步下降。Build 和 Isolation 的通过数整体较高，模型间更明显的差异出现在 Public 和 Hidden 行为检查，说明区分度主要来自行为正确性而非基本可构建性。这里的各项 gate 是独立指标，不应解释为严格嵌套的漏斗。

### 3.2 逐题配对结果比总通过率提供了更多信息

由于四个模型评测的是完全相同的 150 道任务，可以直接比较每对模型在同一道任务上的成败差异，并使用精确 McNemar 检验评估不一致方向是否对称。

| 成对比较（A vs. B） | 共同通过 | 仅 A 通过 | 仅 B 通过 | 共同失败 | 精确检验 $p$ 值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek vs. Qwen3.5 | 53 | 46 | 6 | 45 | $1.03\times10^{-8}$ |
| DeepSeek vs. Qwen3.6 | 53 | 46 | 6 | 45 | $1.03\times10^{-8}$ |
| DeepSeek vs. GPT-OSS | 24 | 75 | 3 | 48 | $5.24\times10^{-19}$ |
| Qwen3.5 vs. Qwen3.6 | 39 | 20 | 20 | 71 | $1.00$ |
| Qwen3.5 vs. GPT-OSS | 18 | 41 | 9 | 82 | $5.61\times10^{-6}$ |
| Qwen3.6 vs. GPT-OSS | 17 | 42 | 10 | 81 | $9.06\times10^{-6}$ |

DeepSeek 相对于两个 Qwen 配置和 GPT-OSS 的优势不仅体现在总通过率上，也得到逐题配对结果的支持。与此同时，Qwen3.5 与 Qwen3.6 虽然均通过 59 道任务，但有 40 道任务的结果不一致，各自独占 20 道成功任务。该现象说明，相同总分可以对应不同的能力结构；论文除报告 leaderboard 外，还应分析模型间的互补成功集合。

### 3.3 任务可解性呈现显著分层

| 解决该任务的模型数 | 任务数 | 占比 |
| ---: | ---: | ---: |
| 0 | 42 | 28.0% |
| 1 | 29 | 19.3% |
| 2 | 33 | 22.0% |
| 3 | 35 | 23.3% |
| 4 | 11 | 7.3% |

150 道任务中，71 道（47.3%）至多被一个模型解决，而仅有 11 道（7.3%）被四个模型全部解决。该分布表明，当前 benchmark 并非由大量“所有模型都能完成”的简单任务主导，同时也保留了能够区分中等与高水平模型的难度梯度。42 道全模型失败任务是后续失败模式分析和难度有效性审计的重点对象。

### 3.4 抽取方式与任务难度相关，但目前仅支持描述性结论

| 抽取方式 | 任务数 | 平均解决模型数 | 平均成功比例 | 任务级 bootstrap 95% 区间 |
| --- | ---: | ---: | ---: | ---: |
| Direct | 56 | 2.20/4 | 54.9% | [47.3%, 62.5%] |
| Adapted | 76 | 1.36/4 | 33.9% | [27.0%, 41.1%] |
| Composite | 18 | 1.00/4 | 25.0% | [12.5%, 38.9%] |

Direct、Adapted 和 Composite 任务呈现出依次降低的平均可解性，Direct 与 Composite 的描述性差距为 29.9 个百分点。这一结果与“抽取过程中需要更多重组和适配时，Agent 更难保持完整行为契约”的假设一致。然而，任务并非随机抽样，抽取类型标签包含人工与 AI 辅助判断，Composite 样本量也较小，因此目前不应将该差异表述为因果效应或总体难度估计。

### 3.5 功能正确不等于抽取紧凑

以下统计仅在 Functional Pass 的提交中计算。RRES 越接近 1，表示提交规模越接近参考实现；复制比例表示提交中与上游仓库重合的代码占比。

| 模型配置 | Functional Pass 数 | RRES 中位数 | 上游代码复制比例中位数 |
| --- | ---: | ---: | ---: |
| DeepSeek V4 Flash | 99 | 0.985 | 97.0% |
| Qwen3.5 122B | 59 | 0.693 | 62.3% |
| Qwen3.6 35B | 59 | 0.816 | 63.6% |
| GPT-OSS 120B | 27 | 0.789 | 26.9% |

DeepSeek 的功能成功率最高，但成功提交的上游代码复制比例中位数也最高。这说明更强的功能正确性并不自动转化为更紧凑、更具选择性的功能抽取，也支持将 compactness 作为独立于 correctness 的评价维度。需要注意，不同模型的统计基于各自通过的任务集合，存在幸存者集合差异，因此该表不能直接解释为无条件的模型紧凑性排名。

### 3.6 当前分析已可用于汇报，但尚不能替代最终主实验

该分析覆盖 600 个唯一的“模型—任务”组合，四个模型均覆盖相同的 150 道任务，不存在重复组合或 taxonomy 连接缺失；244 个 Functional Pass 记录均具有紧凑度数据，主要统计已经过独立复算。因此，这套结果已经足以支撑导师汇报中的现状判断、论文研究问题设计和后续图表选择。

其证据边界仍需明确：12 条记录缺少 evaluator 输出并按归档规则计为失败，48 条记录违反当前声明的上下文额度，历史 evaluator 镜像与现行论文冻结不一致。功能族切片还受到小样本和多重描述性比较影响，token、调用次数和运行时长又受模型服务与运行配置混杂。因此，前者适合放入附录或作为待验证假设，后者暂不宜用于声称基础模型效率差异。最终论文主表仍需由协议完全统一的 Python-200$'$ 结果替换。

完整计算过程、原始表格和可复现实验记录见 [Python-150 探索性分析](../reports/paper_analysis/python150_exploratory_20260830/README.md)，分享前复核结论见 [分析验证报告](../reports/paper_analysis/python150_exploratory_20260830/validation_report.md)。

## 4. 主要缺陷：公开契约的闭合不完整

现有结果呈现出一种反复出现的失败模式，可暂称为 **contract-closure failure**。其含义是：Agent 已经定位或重建了目标能力的主体实现，但未能满足独立包的完整可观察契约。

常见缺口包括：

- 必须导出的函数、类、方法或成员缺失；
- 异常类型、触发条件或精确边界不一致；
- 多步调用和状态机中的状态转换不完整；
- 配置、注释、顺序、schema 或元数据保真不足；
- registry、资源文件、隐式全局状态等传递闭包缺失；
- 目标逻辑存在，但独立安装或依赖闭包不完整。

以 `itsdangerous` 定时签名任务为例，公开契约明确要求签名超过 `max_age` 后抛出 `SignatureExpired`。GPT-OSS 能够通过签名、解签和篡改检测等 Public 主路径，但未保持精确的过期异常语义，因而在 Hidden 边界检查中失败。DeepSeek 能够通过全部功能检查，但提交规模为 323 行，而参考实现为 39 行。该案例同时说明：主路径实现不等于完整契约闭合，功能正确也不等于抽取紧凑。

需要强调的是，contract-closure failure 不是“Hidden 引入额外要求”的同义表述。Hidden 的合法性前提是每项断言均可映射至公开契约。当前分析所关注的是：在契约已经以文本形式公开、但评测测试不可见的条件下，Agent 是否能够自主形成覆盖完整契约的实现和验证证据。

## 5. 已开展的方法与干预实验

方法研究覆盖自生成测试、契约显式化、动态执行、repair、checkpoint、预算控制、上下文管理和自动 prompt 优化等方向。不同实验使用的任务子集、运行时间和对照条件并不完全一致，因此不宜汇总为统一效应量。其主要价值在于检验不同瓶颈假设是否得到支持。

### 5.1 自生成测试与契约推演

| 方法 | 核心假设 | 代表结果 | 证据解释 |
| --- | --- | --- | --- |
| TD-Cognition | 编码前生成探针和行为边界可以改善契约理解 | Flash 12 题：4/12，与 Main 4/12 相同，零翻盘 | 自编探针可能固化 Agent 原有的错误理解 |
| Self-Contract | 由 Agent 自行生成契约检查可以避免遗漏 | Alembic 和 Click 的内部 gate 均通过，Formal Functional 为 0/2 | 可以阻止空提交，但不能保证行为假设正确 |
| Test-First Lift（TFL） | 先对上游生成 characterization harness，再实现目标包 | 1/6，Main 为 2/6；token 约为 Main 的 2.71 倍 | 上游 oracle 真实，但错误的 API 映射会形成错误目标 |
| Verification-aware | 以 verification ledger 组织自测和完成判断 | Distill-24：14/24，低于同日 summary baseline 的 16/24 | 验证记录完整度未转化为 Hidden 成功率 |

上述实验不支持“Agent 仅仅缺少更多自测”的解释。Agent 可以生成大量内部通过的测试，但这些测试往往围绕其已有理解构造；当理解本身存在遗漏时，自测会提供错误的完成信号。

### 5.2 契约检查与可执行反馈

| 方法 | 核心假设 | 代表结果 | 证据解释 |
| --- | --- | --- | --- |
| Exec-Contract | 在实现前注入结构化执行事实和契约检查可以减少语义偏差 | clean-3 中可修复部分 Public，Functional 无翻盘 | 主路径执行事实不足以覆盖完整边界语义 |
| Spec-adversarial | 将公开条款逐项转化为对抗式自检可以提高 Hidden 成功率 | Hidden-4：Main 0/4，方法 0/4；Hidden 0→1 为 0/4 | checker 全部通过仍不能证明完整闭合 |
| Pre-submit audit | 提交前强制进行结构和契约审计可以发现遗漏 | Core-12 为 6/12，低于 summary baseline 的 8/12 | 审计步骤未稳定定位真实行为缺口 |

该组结果表明，将公开契约转换为 checklist 或局部可执行检查有助于排除部分明显错误，但尚不足以生成缺失的边界语义和状态闭包。

### 5.3 Repair 与 checkpoint

| 方法 | 核心假设 | 代表结果 | 证据解释 |
| --- | --- | --- | --- |
| PDR | 差分探针和二次修复可以补齐行为缺口 | held-out 6 题：2/6，与 Main 相同；额外消耗 16.99M token | 额外 probe 和 repair 未形成稳定增益 |
| Rescue+ | 按失败类型分配第二轮修复可以提高成功率 | v2.1 为 3/12，v2.2 为 2/12 | 第二轮 repair 未显示稳定收益 |
| Best-so-far checkpoint | 正确中间包可能被后续编辑覆盖 | 51 道最终失败题的全部独特中间树中，0 道曾经 Functional Pass | 多数失败并非由最后一次编辑覆盖正确答案造成 |

Best-so-far 回放结果收窄了 checkpoint 假设：在已审计的 51 道失败题中，正确解并未在轨迹中短暂出现。因此，仅保留或回滚中间版本无法解决该类失败。

### 5.4 预算与上下文管理

| 方法 | 核心假设 | 代表结果 | 证据解释 |
| --- | --- | --- | --- |
| 旧 Lite V1 | checker、stop 和 repair 可以在维持正确率的同时节省资源 | API Main 144/200 → Lite 131/200；本地 Main 145/200 → Lite 127/200 | token 降低，但正确率下降 6.5--9.0 个百分点 |
| 2M token cap（当前 V1） | 长轨迹后半段主要是无效消耗 | Flash Core-12：8/12 → 4/12；Qwen 干净 E50：35 → 19 | 产生明确的 Functional Pass 税 |
| Adaptive Budget V2 | 根据过程信号动态早停并分配 repair 预算 | Core-12 为 2/12，extra→pass 为 0 | 当前过程信号不足以支持可靠的在线停机判断 |
| Artifact-aware / recency | 更有针对性地保留提交状态和近期上下文可以提高效率或正确率 | Core-12 均为 8/12，与 LLM summary 相同；token 更高 | Functional 持平，资源消耗未下降 |

轨迹分析确实发现，一部分 passing 任务在首次形成可通过包后仍继续消耗大量 token。然而，简单的硬上限或自适应早停会截断仍在后程转化的任务。现阶段可以报告“存在 post-sufficiency token tail”，但尚不能据此提出可靠的在线停机方法。

### 5.5 Public-feedback 信息边界实验

Public-feedback 实验并非候选方法，而是用于检验评测信息边界。同一模型、同一批 12 道任务中，唯一变化是向 Agent 提供 Public 测试，Hidden 始终不可见。

| 条件 | Functional Pass |
| --- | ---: |
| Main：benchmark 测试不可见 | 0/12 |
| Public-feedback | 4/12 |

六道原本 Public 失败的任务在获得 Public 测试后全部通过 Public 层；但五道原本属于 Hidden 失败的成对任务中，有四道 Hidden 结果保持不变。该结果说明，可执行 Public 反馈能够修复部分主路径，但不会自动提供 Hidden 边界信息。Public 失败与 Hidden 失败应被视为同一公开契约的不同评测深度，而不是同一个问题的重复测量。

### 5.6 Self-Harness / AutoSaddler-FLB

仓库中的 `self-harness` 是 AutoSaddler-FLB 的注册别名。该方法在保持 OpenHands、模型、任务、预算和 evaluator 不变的情况下，自动优化四类 prompt 组件：仓库检查、实现策略、自我验证、完成与恢复。

目前已完成集成、配置冻结和两次最小可行性 pilot，但尚未形成有效的 H0/H1 效果比较。

| Pilot | 运行结果 | 证据状态 |
| --- | --- | --- |
| Trial 001 | 开发题 H0 通过；训练题 H0 失败；优化器诊断阶段未返回合格 JSON，mutation 被拒绝 | 真实 OpenHands + evaluator 链路已验证，但未生成 H1 |
| Trial 002 | 训练题和开发题的 H0 均通过，未产生 training failure，也未接受新候选 | 存在 ceiling，无法评估 prompt optimization |

两次 pilot 的 accepted candidate 数均为 0，且每次实际仅完成两个 task-agent rollout，未实现预定的 H0 → H1 成对比较。因此，当前证据既不能证明 Self-Harness 有效，也不能证明其无效；能够确认的仅是工程链路已经打通，而 pilot 设计尚未产生可识别的增益信号。

若继续该方向，需要重新选择具有稳定 H0 失败的训练题和开发题，并解决优化器结构化输出问题。鉴于 Python-200$'$ 主表尚未完成，Self-Harness 的进一步扩展不应高于主表和 Hidden 审计的优先级。

### 5.7 尚无效果数据的 runtime ablation

DeepSeek Harness 和 Codex runtime 的 adapter、版本 pin 和运行入口已经完成，但 Core-12 正式对照尚未产生分数。该工作属于待完成的 runtime ablation，不能作为既有负结果，也不能用于证明当前结论独立于 OpenHands。

## 6. 实验中的关键发现与论文 Takeaways

现有实验除提供模型排名和方法比较外，还揭示了一组能够支撑 Benchmark + Empirical Analysis 论文的规律性现象。以下结论均以当前 FeatureLiftBench、既有模型配置和 OpenHands Official Main 协议为范围；其中跨模型统计来自冻结 Python-150，干预结论主要来自小规模受控实验，最终应在 Python-200$'$ 和代表性轨迹案例上进一步验证。

### 6.1 相同总分可以对应不同的能力结构

Qwen3.5 与 Qwen3.6 均通过 59/150，但二者仅共同通过 39 道任务，并在另外 40 道任务上产生相反结果，各自独占 20 道成功任务。由此可见，单一 Pass@1 排名会掩盖模型的互补性：两个总分相同的 Agent 可能依赖不同的能力组合，也可能在不同任务机制上失败。

**论文 Takeaway：** repository-level benchmark 不应只给出总通过率，还应报告任务级成对差异、互补成功集合和按任务机制划分的能力画像。这使 benchmark 从排行榜扩展为模型行为诊断工具。

### 6.2 当前 Agent 的困难往往发生在“能够构建”之后

四个模型的 Build 与 Isolation 通过数整体较高，而 Public、Hidden 和最终 Functional 结果明显更低。例如，DeepSeek 的 Build 为 144/150，但 Functional 为 99/150；Qwen3.5 的 Build 为 150/150，Functional 仅为 59/150。结合 `itsdangerous` 等案例可以看到，Agent 往往能够形成可安装、可导入的独立包，却遗漏异常类型、状态转换、元数据或边界行为。

**论文 Takeaway：** 功能抽取的核心难点不是生成一个“形似目标”的包，而是在 test-blind 条件下闭合完整的可观察契约。Build、Public、Hidden、Isolation 和 Functional 的分层评测能够定位失败发生在结构闭包还是行为闭包。

### 6.3 更高的功能正确率不必然意味着更好的抽取

DeepSeek 的 Functional Pass@1 最高，但其成功提交的上游代码复制比例中位数达到 97.0%；两个 Qwen 配置分别为 62.3% 和 63.6%，GPT-OSS 为 26.9%。该结果不能直接构成无条件的模型紧凑性排名，因为不同模型的成功任务集合不同，但至少表明高正确率可以通过更保守、更大范围的代码复用实现。

**论文 Takeaway：** correctness 与 compactness 是两个不可相互替代的评价维度。只评价功能通过率会奖励“尽可能多地复制上游”的保守策略，而忽略功能抽取对独立性、最小依赖和选择性迁移的要求。

### 6.4 自生成测试可能验证 Agent 已有的错误理解

TD-Cognition、Self-Contract、TFL、Verification-aware 和 Spec-adversarial 等方法均增加了测试、探针、ledger 或契约检查，但未形成稳定的 Functional 增益。部分实验中，Agent 生成的内部检查全部通过，正式 evaluator 仍然失败。这说明自测数量增加并不等价于契约覆盖增加；当 Agent 对接口、状态或边界的初始理解存在遗漏时，自生成测试可能围绕同一错误假设形成自证闭环。

**论文 Takeaway：** test generation 的关键不是生成更多与当前实现一致的测试，而是获得独立于当前实现假设的反事实、边界和差分证据。未来方法应重点研究“如何发现尚未被 Agent 表述的契约”，而不是继续强化同源自检。

### 6.5 多数失败并非由最后一次编辑破坏正确答案

对 51 道最终失败任务的全部独特中间树进行回放后，没有发现任何曾经通过完整 Functional gate 的中间版本。该结果不支持“Agent 已经得到正确解，只是在后续编辑中将其覆盖”的主要解释，也说明单纯保存 best-so-far、回滚或扩大 repair 轮数不会自动解决问题。

**论文 Takeaway：** 很多失败轨迹的根本问题是正确候选从未被生成，而不是正确候选未被保存。方法研究需要改善假设形成、契约发现和候选多样性，而不能仅依赖更强的 checkpoint 与后处理。

### 6.6 长轨迹中的无效消耗与有效后程转化同时存在

轨迹中可以观察到一部分 passing 任务在首次形成可通过包后仍继续消耗大量 token，即 post-sufficiency token tail；但简单压缩预算又会显著降低正确率。Flash Core-12 在 2M token cap 下由 8/12 降至 4/12，Qwen 干净 E50 由 35 降至 19，现有 Adaptive Budget 也未识别出稳定的在线停止信号。

**论文 Takeaway：** “长轨迹存在浪费”并不推出“统一早停能够无损提效”。代码 Agent 的在线停机需要区分已经充分完成、仍在形成关键行为闭包以及陷入无效循环三种状态；当前基于表面进度或固定预算的信号不足以完成该判断。

### 6.7 Public 反馈能够修复可见主路径，但不会自动补齐不可见边界

在同一模型和同一批 12 道任务上，仅开放 Public 测试即可使 Functional 从 0/12 提高到 4/12，六道原本 Public 失败的任务全部通过 Public 层；但五道原本属于 Hidden 失败的成对任务中，有四道 Hidden 结果保持不变。该实验说明，可执行反馈对可见行为具有直接修复价值，但不会自然产生测试未揭示的异常语义和边界状态。

**论文 Takeaway：** Public 与 Hidden 不是简单重复的两组测试，而是对同一公开契约的不同证据深度。该信息边界为研究 test-aware repair 与 test-blind contract reasoning 的差异提供了受控实验基础。

### 6.8 AI 时代的瓶颈可能从代码生产转向代码演化

当前 Agent 已经能够在大量任务上生成可构建、可安装的实现，但从 Build 到 Functional 的明显落差、成功提交中的 copy-heavy 现象，以及多种自测和 repair 干预未能稳定改善结果，共同说明“生成更多代码”并不自动解决后续模块化和维护问题。对于由 Agent 快速生成、经过产品使用验证但缺少充分人工理解的项目，这种差距会直接表现为重构风险：维护者知道系统当前能够工作，却无法确认拆分、迁移或瘦身后是否仍保持完整行为。

**论文 Takeaway：** 下一阶段代码 Agent 的关键能力不应只包括根据需求增加实现，还应包括对既有实现进行行为保持的删除、拆分、迁移和依赖治理。FeatureLiftBench 提供了一个可复现的 maintenance-after-generation 评测，用于衡量 Agent 能否安全地演化由人或其他 Agent 产生的代码。

综合来看，这些发现共同说明：FeatureLiftBench 的价值不仅是衡量模型能完成多少任务，还在于揭示模型如何成功、在哪里失败，以及常见干预为何未能改变失败机制。即使现阶段尚无稳定增益的新方法，上述负结果和诊断性发现仍可形成 Benchmark + Empirical Analysis 论文的核心经验贡献。

## 7. 方法实验形成的综合判断

现有实验对三类直觉性解释进行了收窄。

第一，主要问题并非单纯缺少自测。TD-Cognition、Self-Contract、TFL 和 Verification-aware 均强化了测试或验证过程，但未稳定提高 Functional Pass。一部分方法的内部检查全部通过，正式评测仍然失败。

第二，主要问题并非正确中间版本被最终编辑覆盖。对 51 道失败题的中间树回放未发现任何曾经通过完整 Functional gate 的版本。多数失败轨迹中并未产生可供 checkpoint 恢复的正确解。

第三，主要问题并非预算分配策略本身。Passing 轨迹中存在明显的 post-sufficiency token 消耗，但简单限额和现有早停信号会损失正确率。资源效率与功能正确性之间存在真实权衡，尚不能由单一停止规则解决。

因此，当前证据更支持以下判断：

> 当前代码 Agent 已具备较强的仓库定位、实现复用和局部改写能力，但仍缺少在 test-blind 条件下形成完整契约覆盖证据的可靠机制。围绕既有理解增加自测、checklist 或 repair，并不能稳定补充其尚未识别的边界语义。

这一判断是基于多组描述性和小规模干预证据形成的研究结论，不应被表述为已经确立的普遍因果机制。其外推范围目前限于 FeatureLiftBench、现有模型配置和 OpenHands Official Main 协议。

## 8. 论文定位与预期贡献

基于当前证据，论文拟定位为 Benchmark + Empirical Analysis，而不再以新 Agent 方法作为主贡献。预期贡献包括以下四个方面。

从现实问题看，论文关注的是 AI 辅助开发的后半程：当代码已经被快速生成并进入使用后，Agent 是否能够在缺少实现知识的情况下对其进行安全重构和能力迁移。该定位使 FeatureLiftBench 与主要评价 issue repair 或一次性代码生成的 benchmark 形成互补，也为 AI-generated code、传统遗留系统和单体应用的后续治理提供共同的评测抽象。

### 8.1 新任务定义

形式化 repository-level, behavior-preserving feature extraction，明确该任务要求同时完成目标定位、行为与依赖闭包以及独立化交付，并将其与 issue repair、代码定位和绿场生成区分开，将 maintenance after generation 纳入代码 Agent 的可评测能力范围。

### 8.2 可复现 Benchmark

构建 Python-200$'$ 主套件，包括 200 道来自 176 个真实开源仓库的任务、固定源码版本、公开行为契约、确定性 Docker evaluator、依赖闭包和任务级审计信息，并使用 Hard-50 提供难度校准。

### 8.3 正确性与紧凑性的双轴评价

以 Functional Pass@1 评价独立包的功能正确性，以 RRES、复制比例和依赖 footprint 评价抽取紧凑性，同时报告 Build、Public、Hidden 和 Isolation 的行为深度，避免单一分数掩盖不同失败类型。

### 8.4 Agent 能力与失败机理分析

系统分析跨模型能力梯度、任务级互补成功、contract-closure failure、Public/Hidden 信息边界、功能正确性与紧凑度分离、post-sufficiency token tail，以及多类合法脚手架未能稳定提升 Functional Pass 的原因。

论文的工作性中心命题为：

> FeatureLiftBench shows that current code agents can often locate and reconstruct repository functionality, yet still struggle to close the full observable contract of an independent package under test-blind evaluation; functional correctness and extraction compactness remain distinct capabilities.

该命题仍需由合格的 Python-200$'$ 主表、Hidden 公平性审计和代表性轨迹案例进一步支撑。

## 9. 论文结构建议

1. **Introduction：** 说明功能抽取与 issue repair、代码定位和从零生成的区别；
2. **Task Definition：** 定义 Full-Repository / No-Hint / test-blind 协议；
3. **Benchmark Construction：** 介绍 Python-200$'$、源码冻结、Hard-50 和 taxonomy；
4. **Evaluation：** 定义 Functional Pass、RRES、失败深度和资格审计；
5. **Main Results：** 报告合格的跨模型主表和任务级成对比较；
6. **Empirical Analysis：** 分析 contract closure、代表性案例、Public/Hidden、紧凑度和 token 尾部；
7. **Intervention Evidence：** 分组报告自测、契约检查、repair、budget 和 Self-Harness 等实验；
8. **Discussion and Threats：** 讨论 Hidden 公平性、runtime 依赖、attempt=1 随机性和标签可靠性；
9. **Related Work and Conclusion。**

方法实验在该结构中的作用是检验失败解释和信息边界，而非构成独立的方法主表。

## 10. 当前证据缺口与下一步计划

### 10.1 形成合格的 Python-200$'$ 主表

当前首要问题是实验镜像身份。可行方案包括：

1. 找回与原结果包一致的 agent / evaluator 镜像，对 84 道严格替换任务进行重跑；
2. 使用当前固定镜像，对完整 200 道任务进行干净重跑。

第二种方案成本更高，但能够形成更一致、审计路径更清晰的论文主表。

### 10.2 补充新套件跨模型结果

现有四模型完整比较仅覆盖冻结 Python-150。若论文需要形成跨模型能力结论，应在 Python-200$'$ 上补充若干具有代表性的模型配置，并保持 OpenHands、预算、上下文策略、任务冻结和 evaluator 一致。

### 10.3 完成 Hidden 公平性审计

需要逐条确认 Hidden 断言均可映射至公开契约，并记录争议条款的处理过程。为增强可信度，建议引入第二视角复核，并在论文中报告审计协议、通过标准和排除规则。

### 10.4 补充必要的稳健性证据

- 在分层任务子集上进行重复运行，以估计 attempt=1 的随机性；
- 完成至少一个第二 Agent runtime 对照，以界定 OpenHands 依赖；
- 对 taxonomy 标签进行人工复核；
- 在同一批共同通过任务上比较紧凑度，减少 pass-conditioned survivor bias。

在完成合格主表和 Hidden 审计之前，不建议继续横向扩展新的方法臂。Self-Harness 如需继续，应在上述核心证据完成后，以重新设计的稳定 H0 失败题开展成对试验。

## 12. 结论边界

现阶段可以支持的结论包括：

- FeatureLiftBench 在冻结 Python-150 上呈现明确的跨模型能力梯度；
- 模型主要在 Public 和 Hidden 行为检查上产生差异；
- 相同总通过率可能掩盖显著的任务级能力差异；
- 功能正确性与抽取紧凑性是相互独立的评价维度；
- 已完成的自测、契约检查、repair、预算和上下文脚手架未显示稳定的 Functional Pass 增益；
- Public 可执行反馈能够修复部分主路径，但不能普遍消除 Hidden 失败；
- Self-Harness / AutoSaddler-FLB 已完成工程链路验证，但尚无可判断的方法效果证据。

现阶段不能支持的结论包括：

- 将 132/200 作为 Python-200$'$ 的正式通过率；
- 将 Self-Harness 的 development score 1.0 解释为方法提升；
- 认定 Self-Harness 已被证明有效或无效；
- 认定当前模型已经解决仓库定位问题；
- 将 post-sufficiency token tail 直接转化为可用的在线早停规则；
- 将现有小规模方法实验换算为全套件效果；
- 将当前结论无条件外推至其他 Agent runtime 或其他编程语言。
