\title[FeatureLiftBench: Behavior-Preserving Feature Lifting]{FeatureLiftBench: Benchmarking Behavior-Preserving Feature Lifting from Real Repositories}
\author{Anonymous Author(s)}

\begin{abstract}
Reusing existing software requires preserving a capability after moving it
beyond its original project boundary. We introduce \flb, a benchmark for
\emph{behavior-preserving feature lifting}: given an intact source repository
and a public behavioral contract, a coding agent builds a new package that
runs without access to the source repository. The release contains 200 Python
tasks from 176 repositories and 182 snapshots. Validation combines automated
checks, AI-assisted review, author review, and reference replay.
We compare six configurations on 150 common tasks and extend five to the
remaining 50. Functional pass rates range from 24.0\% to 76.7\%.
The results expose a \emph{contract-closure gap}: DeepSeek V4 Pro and
DeepSeek V4 Flash deliver packages for every task, yet 76 of their 77 combined
failures first occur at behavioral gates; inspected artifacts omit required
behavior despite implementing substantial parts of the target capability.
Equal functional success also permits different extraction strategies.
On 97 common passing tasks, Pro and GPT-5.6 Luna have median direct source
overlap of 0.966 and 0.191, respectively (paired $p=1.18\times10^{-13}$).
We jointly report functional correctness, successful-artifact characteristics,
and observed execution effort. \flb exposes the gap between producing a
package and preserving a capability across a new software boundary.

\end{abstract}

\section{Introduction}
\label{sec:introduction}

Software reuse often requires moving an existing capability across project
boundaries. A developer may need a parser from a larger tool, configuration
handling from a framework, or a signal registry for a new library. The source
repository supplies an implementation, but the capability may extend beyond
any single file or function. Its behavior can depend on supporting modules,
shared data and state, framework mechanisms, and configuration or resource
loading. For example, extracting a signal dispatcher may require preserving
sender-specific subscriptions, weak-reference cleanup, and namespace identity
alongside the callback loop. Access to the implementation therefore leaves an
important question: \emph{can a coding agent use a complete source repository
to deliver a specified capability as a behaviorally correct, independently
executable package?}

We formulate this task as \emph{behavior-preserving feature lifting}, or
\emph{feature lifting} for short. Given an intact, version-pinned source
repository and a public contract specifying the target interface and behavior,
an agent constructs a new package that is evaluated without access to the
source repository. The agent may extract, adapt, or reimplement code; the
contract determines what the resulting package must do. Correctness is thus
judged at the new package boundary, where supporting behavior previously
provided by the source project must be accounted for. Feature lifting connects
repository understanding to a concrete reuse outcome: an existing capability
made available as an independent software component.

Figure~\ref{fig:pipeline} illustrates the motivation: behavior supported by the
original project may depend on code, state, or framework assumptions that must
be resolved when reconstructing the capability across a new package boundary.
The evaluation therefore targets the submitted package without runtime access
to the source repository.

Existing benchmarks emphasize two related objectives: \emph{modify an existing
repository} and \emph{implement a requested feature}. SWE-bench and SWE-Bench
Pro evaluate changes whose execution target remains the existing
project~\cite{jimenez2024swebench,deng2025swebenchpro}. FeatBench and
FeatureBench evaluate feature development, with FeatureBench covering both
incremental and from-scratch settings~\cite{chen2026featbench,zhou2026featurebench}.
\flb instead asks agents to \emph{reconstruct an existing capability from
intact implementation evidence across a new software boundary}: its input is
a complete source repository plus an output contract, its deliverable is an
independent package, and its target is source-free functionality. FeatureBench's
from-scratch setting does not supply the complete implementation of the target
feature. Making that implementation available changes the challenge from
inventing behavior to recovering and reorganizing the behavior needed after
the original project context is removed. Software transplantation has studied
extracting behavior from a donor program and adapting it to a host
program~\cite{barr2015transplantation}; we bring this reuse objective to an
executable benchmark for general-purpose coding agents.

We introduce \flb, comprising \textbf{200 tasks from 176 Python repositories
and 182 pinned snapshots}. Each task supplies the complete source repository
and a public behavioral contract. Agents explore the source without
benchmark-provided location hints, benchmark tests, or reference solutions,
and deliver the requested functionality in a new package. The evaluator checks
loading, behavior, and isolation without access to the source repository.
Here, independence means that the package is loadable and executable under the
benchmark environment; release-ready packaging is not a requirement.
Construction combines automated consistency checks and reference execution
with AI-assisted review and author review. The task taxonomy describes
three lift types and four entanglement mechanisms.

Our primary comparison evaluates \textbf{six configurations on the same
150 tasks}; five configurations additionally cover the remaining 50 tasks in
an extended evaluation. The common comparison uses the same task set and
information policy, with configuration differences documented in
Section~\ref{sec:protocol}. Functional pass rates range from
\textbf{24.0\% to 76.7\%}. Strong agents reliably deliver packages, yet
behavioral preservation remains the dominant observed failure boundary:
DeepSeek V4 Pro and DeepSeek V4 Flash deliver packages for all 150 tasks and
have no Build-first failures, but 76 of their 77 combined failures first occur
at a behavioral gate. This contract-closure gap is illustrated by artifacts that preserve a visible
operation while omitting another required behavior. Task-level analysis shows
heterogeneous success and a strong construction-cohort association; the apparent
lift-type gradient is not supported as an independent difficulty effect after
controlling for model and construction composition.

We characterize successful artifacts using reference-relative implementation
size and detected direct source overlap, and report execution steps and token
usage where verifiable. On the 97 tasks passed
by both DeepSeek V4 Pro and GPT-5.6 Luna, the former produces larger artifacts
on 85 and greater source overlap on 76. The paired copy difference is substantial ($p=1.18\times10^{-13}$): successful
reuse can emerge from markedly different amounts of retained source code.
Correctness, extraction characteristics, and effort therefore provide
complementary views, with behavior preservation as the prerequisite for
interpreting successful-artifact measurements.

The paper makes three contributions:
\begin{itemize}
 \item \textbf{A task and benchmark for behavior-preserving reuse.} We
 formulate feature lifting from intact source evidence across a new package
 boundary and instantiate it with 200 tasks from 176 repositories
 (Section~\ref{sec:benchmark}).
 \item \textbf{Construction, validation, and executable evaluation.} We
 combine explicit contracts, protected tests, AI-assisted review, author
 semantic review, and reference replay with source-free evaluation of submitted
 artifacts (Sections~\ref{sec:validation} and~\ref{sec:protocol}).
 \item \textbf{Evidence on current feature-lifting capabilities.} We report
 a six-configuration comparison on 150 common tasks and extended evaluation
 on 50 additional tasks, analyze task structure and behavioral failures, and
 additionally characterize successful artifacts by size and source overlap
 (Sections~\ref{sec:results} and~\ref{sec:diagnostics}).
\end{itemize}

\section{The FeatureLiftBench Benchmark}
\label{sec:benchmark}

The benchmark connects a reuse request to an observable deliverable. We first
define the contract and package boundary, then describe how source evidence,
task specifications, and executable checks are assembled. Validation records
and dataset composition establish the scope of the resulting collection.

\subsection{Task Formulation and a Running Example}

A task consists of a pinned repository $R$, a public contract $S$, an initial
workspace $W$, and a protected evaluator $J$. A model backend $M$ acting through
an agent harness $H$ produces a submission $A$:
\begin{equation}
 A = \operatorname{Run}(M,H,R,S,W).
\end{equation}
The public contract lists the required API surface, behavior clauses, constraints,
and exclusions. Source identity records establish which upstream snapshot defines
the behavior being lifted. The agent can inspect that snapshot but must place the
result inside the designated submission directory.
A standalone package here means an independently loadable and executable
artifact under the benchmark environment, without runtime access to the source
repository; the task does not require distribution-ready wheel packaging.

The contract determines the scope of preservation. A task may require a selected
configuration operation or registry behavior without requiring the entire
upstream project. APIs, return values, exceptions, mutation, ordering, or resources
are obligations when specified by the task. Direct extraction, adapted code, and
reimplementation are legal strategies. This permits multiple passing artifacts
and avoids grading against a single required source slice.

The functional score is
\begin{equation}
 F(A)=B(A)\land T_{\mathrm{public}}(A)\land T_{\mathrm{hidden}}(A)\land I(A),
 \label{eq:functional}
\end{equation}
where $B$ is the evaluator's package loading/build gate, $T$ denotes the two
behavioral test groups, and $I$ denotes its explicit isolation checks. The tests
execute in an environment without the source repository. Consequently, a
dependency on a missing source path can fail during loading or behavioral tests,
before the separate Isolation gate becomes the first failing gate. Gate names
must not be interpreted as independent semantic failure causes.

\paragraph{Running example: a signal registry.}
The Blinker task provides a concrete instance of the general task in
Figure~\ref{fig:pipeline}. It asks for \texttt{Signal} and \texttt{Namespace}, together
with supporting dispatch logic, under the new \texttt{featurelifted} namespace. The public contract requires
sender-specific dispatch (including the \texttt{ANY} sender sentinel), receiver
responses, cleanup of weak receivers after
garbage collection, stable signal identity within a namespace, and scoped
connection/disconnection. It excludes asynchronous receivers and the upstream
global named-signal singleton. A plausible dispatcher can therefore remain
incomplete even if its main \texttt{connect} and \texttt{send} methods work:
receiver lifetime and namespace identity are also part of the requested behavior.
The final artifact may retain upstream code or reimplement these obligations,
but may not import \texttt{blinker} or read the source tree at runtime.


\subsection{Task Construction}
\label{sec:construction}

Construction turns a reusable capability into a bounded contract, protected
behavioral tests, and a source-independent reference implementation.
Figure~\ref{fig:construction} separates this construction process from the
complementary validation evidence supporting the frozen release.

\paragraph{Select a capability and pin its source.}
Tasks come from Python libraries, developer tools, and framework components.
Selection favors inspectable implementations, supporting tests or documentation,
a scope that can be stated explicitly, and execution without live services.
Examples include parsing, configuration resolution, registries, and resource
handling. Each task is tied to a pinned source snapshot. Agents receive the
complete tracked source tree, including upstream tests and documentation, with
uniform exclusions for repository administration and untracked artifacts.
Files are not pruned to the target feature, so identifying its implementation
and supporting dependencies remains part of the task.

\paragraph{Specify the observable contract.}
The public specification defines the exported APIs, signatures, defaults,
exceptions, and behavioral obligations, together with explicit exclusions and
permitted dependencies. For example, the signal-registry task retains receiver
lifetime and namespace identity while excluding asynchronous dispatch.
The task statement is generated from this specification. Source-location hints
and evaluator metadata are omitted from the agent view, separating the requested
behavior from a prescribed implementation strategy.

\paragraph{Build protected tests and a reference artifact.}
Each task includes Public tests for primary contract behavior and Hidden tests
for additional cases and combinations. Both groups are withheld from the agent.
Test-to-contract mappings associate checks with required APIs and behavioral
clauses; excluded behavior must not become an undeclared test requirement.
A reference implementation demonstrates that the contract can be satisfied
without runtime access to the source repository. It is a feasible solution and
measurement reference, not a unique required implementation.

\paragraph{Assemble and freeze the release.}
Validated task packages are versioned with their specifications, source
snapshots, tests, references, and execution policies. The release contains
200 tasks from 176 repositories and 182 snapshots. Appendix~\ref{app:provenance}
provides the task index and validation details.

\subsection{Benchmark Validation}
\label{sec:validation}

Validation combines automated checks, AI-assisted review, author semantic
review, and reference execution. These activities address complementary
questions: whether the assets agree, whether their behavioral expectations are
appropriate, and whether the evaluator can execute a correct independent artifact.

\paragraph{Automated consistency checks.}
Checks cover source mappings, required files and metadata, dependency declarations,
generated task statements, and test-to-contract mappings. All 200 task packages
pass the recorded structural checks; source records map them to 182 verified
snapshot archives. These checks detect inconsistencies such as stale statements,
missing API declarations, and mappings to nonexistent tests.

\paragraph{AI-assisted audit and author semantic review.}
The paper authors conducted semantic review alongside AI-assisted checks.
The authors completed review of all 200 retained task packages, with
AI-assisted checks supporting the review.
The review covered task and test semantics, lift-type and
entanglement labels, and failure annotations. Its criteria concern whether
requested behavior is supported by the source, whether tests stay within the
public contract, whether labels describe the requested transformation and its
dependencies, and whether failure interpretations are supported by the artifact.
AI-assisted checks supplied review evidence for author inspection. Problematic
candidates were excluded during construction. Reviewer involvement and the
limits of finite tests are discussed in
Section~\ref{sec:threats}.

\subsection{Dataset Composition}
\label{sec:suite}

Figure~\ref{fig:construction} distinguishes construction from completed validation.
FeatureLiftBench contains 200 Python tasks. The main comparison evaluates six
configurations on the same 150 tasks: all six have results on these task IDs,
and their passing submissions have the reference-relative measurements used
in this paper. Five configurations also have results on the remaining 50 tasks;
Pro was evaluated on the 150-task subset. Appendix~\ref{app:extension} reports
these additional outcomes. The evaluation coverage determines which results
can be compared; it does not define separate difficulty tiers.

\paragraph{Source and functional coverage.}
Canonical repository IDs in the freeze identify 126 repositories and 132
snapshots in the evaluated 150-task set, plus 50 repositories and 50 snapshots
for the remaining tasks.
The repository sets are disjoint, yielding 176 repositories and 182 snapshots
in the complete release. Repository aliases are normalized before counting.
These units distinguish the number of extraction tasks from both project
diversity and the number of pinned source versions.

The existing task-family inventory spans ten groups. Joined to the release by
task ID, its largest groups are registry/plugin dispatch (38 tasks),
parsing/tokenizing/decoding (37), configuration resolution/discovery (26),
validation/normalization/construction (22), and serialization/formatting/rendering
(19). The remaining 58 tasks cover workflow/session orchestration, resource and
metadata loading, algorithms and data structures, protocol state transitions,
and cache/retry policies. These groups describe functional breadth. The two structural dimensions below
support more focused comparisons of lifting behavior.

\paragraph{Lift types and representative tasks.}
\label{sec:lift-types}
We describe task structure along two dimensions: the relationship between the
requested capability and the upstream implementation, and the mechanisms that
connect that capability to its host project. The first dimension assigns one
lift type per task. \emph{Direct} preserves the behavior of an identifiable
upstream capability while extracting and decoupling it. \emph{Adapted} retains
an identifiable upstream capability but requires a declared transformation of
its interface or behavior, such as changing parameters, return values, or
exception handling. \emph{Composite} combines multiple capabilities or
reconstructs a workflow without a single corresponding upstream API. These
labels characterize the requested transformation; they do not prescribe how
an agent must implement its answer.

Across the complete 200-task release, 68 tasks are Direct, 100 Adapted,
and 32 Composite. Figure~\ref{fig:coverage}(a) shows their distribution
across the ten functional families.

The Direct-labeled Blinker task illustrates preservation of a coherent signal
registry, including interactions beyond its most visible dispatch operation.
The Adapted-labeled \texttt{build} task exposes source-directory validation and
build-system-table parsing under the new package API, while excluding network

boundary selects validation behavior from a larger build workflow. As a
Composite example, the \texttt{zope.interface} task among the remaining 50 tasks combines
interface declarations, inheritance, named adapter registration, and single-
and multiple-object adapter queries. The lift-type inventory covers all 200 tasks;
Section~\ref{sec:validation} describes author review and AI-assisted review.

\paragraph{Four entanglement mechanisms.}
\label{sec:entanglement}
The second dimension describes dependencies that must be accounted for when
moving the capability across a package boundary. We organize the existing
fine-grained entanglement labels into four broader categories:
\begin{itemize}
 \item \textbf{Code dependencies:} behavior relies on internal helpers,
 transitive imports, implicit runtime dependencies, or third-party interfaces
 whose behavior the extracted component must preserve or accommodate.
 \item \textbf{Data and state:} correctness depends on shared data-model
 invariants, parser context, or global state and registries that must remain
 consistent across operations.
 \item \textbf{Framework mechanisms:} a capability operates through lifecycle
 stages, registration and dispatch, or dynamic loading and plugin discovery
 supplied by its host framework.
 \item \textbf{Environment and resources:} behavior depends on configuration,
 environment and path rules, or packaged resources that must remain available
 and correctly interpreted in the standalone artifact.
\end{itemize}

These categories allow multiple labels per task. For example, the Direct
Blinker task still requires coherent receiver state and namespace identity,
as well as registration and dispatch behavior: its lift type does not remove
data/state or framework obligations. Thus lift type describes the requested
transformation, while entanglement describes the dependencies to be handled;
neither is an assigned difficulty level or a measured failure cause.
Appendix~\ref{app:entanglement-mapping} gives the mapping from the ten existing
mechanism labels. The labels support descriptive, within-category comparisons in
Section~\ref{sec:rq3}. Lift types partition the tasks; entanglement mechanisms
overlap and therefore do not define independent experimental groups.

\section{Evaluation Protocol and Experimental Setup}
\label{sec:protocol}

Our primary comparison evaluates six configurations on the same 150 tasks
from the 200-task benchmark. Five configurations additionally cover the
remaining 50 tasks (Appendix~\ref{app:extension}). We describe the shared
information policy, agent settings, scoring rules, and statistical analysis.

\subsection{Information Boundary and Agent Configurations}

We evaluate DeepSeek V4 Pro, DeepSeek V4 Flash, GPT-5.6 Luna served through
OpenLux, GLM-5.3-Flash, Qwen3.6-35B-A3B-FP8, and GPT-OSS 120B. Below, we
abbreviate them as Pro, Flash, Luna, GLM, Qwen, and OSS. The agent image records
OpenHands CLI 1.16.0 with native tool calling. The common protocol supplies the complete pinned repository,
withholds benchmark tests and source-location hints, and uses the standard task
prompt. Agents can inspect upstream tests and create their own probes.

The configured envelope is 120 steps, 131,072 context tokens with 8,192 reserved,
and a 3,600-second task timeout. The protocol imposes no separate total-token
cap. Runtime statistics such as recorded
assistant messages are not necessarily identical to the configured action budget.
The evaluated object is a backend embedded in its recorded OpenHands/provider
profile, not a base model independent of tool calling, serving, and recovery.

Pro and Flash use token-based context condensation, while the other four
backends retain the default. Appendix~\ref{app:reproduction} gives the
detailed settings and result-file organization.


\subsection{Functional Evaluation and Extraction Metrics}

Only the collected submission enters the evaluator capsule. The source
repository is absent from the runtime import path, dependencies are fixed,
and the container disables networking. The evaluator policy specifies
Linux/amd64, Python 3.11.14, a read-only root filesystem, and dropped
capabilities. Run records retain the agent and evaluator image identifiers.

\textbf{Build} resolves and loads the submitted package according to the
evaluator's installation/path-loading policy. In this release, a direct package
directory can be loaded through \texttt{PYTHONPATH}; an editable-install failure
can also use a path fallback. Thus a Build pass demonstrates usability under the
frozen evaluator policy, not that a wheel or clean package-manager installation
has been independently validated. \textbf{Public} tests exercise primary
contract behavior, and \textbf{Hidden} tests cover additional cases and
combinations intended to follow the same public contract. \textbf{Isolation}
checks include forbidden source imports and protected-path restrictions.
All four outcomes are required by Equation~\ref{eq:functional}.
Both Public and Hidden tests are withheld from agents in the evaluated
protocol; the names identify evaluator test groups.


We report two complementary views. An exclusive first-outcome classification
uses Missing, Build, Public, Hidden, then Isolation, with Pass for a fully
successful artifact. A non-exclusive view counts failed gate flags among
delivered artifacts; these counts can overlap. A failed flag can reflect a
preceding loading failure and is not necessarily evidence that all tests in that
group executed. \emph{Isolation residual} denotes artifacts that pass Build,
Public, and Hidden but fail Isolation. This is a measured residual category,
not the prevalence of all source-dependency mistakes.

\paragraph{Artifact characteristics and efficiency.}
\label{sec:metrics}

For a passing artifact $A$ and a frozen feasible reference $A_{\mathrm{ref}}$,
Reference-Relative Extraction Size is
\begin{equation}
 \operatorname{RRES}(A)=
 \frac{\operatorname{PythonLOC}(A)}{\operatorname{PythonLOC}(A_{\mathrm{ref}})}.
 \label{eq:rres}
\end{equation}
The evaluator uses its Python source-line counting convention consistently for
both artifacts. An RRES of one means equal counted size, not equal code or
optimality. The reference demonstrates one feasible implementation; it is not a
proof of a minimum semantic closure.

The copied-code diagnostic estimates the fraction of submitted lines matched
to source code in runs of at least three normalized non-empty, non-comment
Python lines. It can miss rewritten equivalents and count shared idioms. It is
neither a licensing judgment nor a direct measure of maintainability. These
metrics are computed in a trusted read-only stage after functional evaluation;
the metrics stage does not execute the submitted code.

Footprint summaries are conditioned on functional success. Because different
backends pass different tasks, unpaired medians are descriptive only. Comparisons
between backends use their same-task common passing set. Low RRES or low detected
copying cannot compensate for a functional failure, and neither is folded into
the primary pass score.

\paragraph{Execution effort.}
Table~\ref{tab:main} reports the median and 90th percentile of recorded assistant
steps over all 150 assigned tasks per configuration, including failures.
Token statistics use only verified accounting: uncached prompt plus completion
tokens for Pro/Flash and provider total tokens for Qwen/OSS. Luna/GLM have no
verified token totals. The token columns retain these definitions explicitly;

\subsection{Comparison Scope and Statistical Protocol}

The primary comparison contains 900 model--task outcomes: one retained final
outcome for each of six configurations on each of the 150 common tasks.
The remaining 50 tasks extend benchmark coverage for five configurations.
We use the common set for all six-configuration comparisons and report the
additional outcomes in Appendix~\ref{app:extension}.

Empty submissions remain failures, including tool-validation and early-exit
events. Correctness is determined by the evaluator, independently of agent
run status. The collection procedure permits preflight replacements and
runner-level recovery from transient errors. We use the final collected
outcome under this procedure, rather than treating recovery events as
independent trials or estimating success across repeated runs.

\paragraph{Input and result consistency.}
The saved initial prompts, dependency locks, and recorded source identities
agree with the task definitions for all 900 outcomes. All available evaluator
capsule digests agree with the corresponding task inputs, and all 900 run
records use the same agent/evaluator image-ID pair. The result matrix is
checked for unique model--task cells, identical task membership across
configurations, and agreement with the saved evaluator outcomes.
Appendix~\ref{app:reproduction} describes the evidence files and analysis
entrypoint. Configuration-specific context handling and provider behavior
remain part of the evaluated systems.


We retain Wilson intervals in the analysis artifact and report selected
two-sided exact McNemar tests for paired model outcomes. Reported $p$-values are
unadjusted exploratory comparisons; they do not establish a total ordering of
backends. To describe task variation, we count how many configurations pass each task
and use the saved logistic analysis controlling for model, construction cohort,
and lift type, with standard errors clustered by task ID. This empirical frequency does not assign a
permanent difficulty label.
For paired copying we report Wilcoxon signed-rank tests and matched-pairs
rank-biserial effect sizes.

One retained observation per cell does not estimate stochastic run-to-run
variance. Multiple tasks from a repository can also share behavior and failures;
task-level intervals do not model every repository-level dependence.

The four research questions follow the path from attempted reuse to a delivered
artifact. We first measure functional success, then examine failure stages and
variation across tasks. Finally, comparisons on common successes reveal
implementation differences that a pass/fail score alone does not describe.

\subsection{RQ3: How Does Difficulty Vary across FeatureLiftBench Tasks?}
\label{sec:rq3}

\paragraph{A heterogeneous solve-frequency spectrum.}
The right panel of Figure~\ref{fig:failures} shows the number of configurations
passing each task: 28 tasks (18.7\%) are passed by none, 17 (11.3\%) by all six,
and 105 (70.0\%) have mixed outcomes. These observations characterize task
variation under the evaluated configurations, rather than assigning fixed
difficulty tiers.

\paragraph{Construction composition accounts for a substantial difficulty contrast.}
The frozen analysis distinguishes a later 50-task construction cohort from the
other 100 tasks within the common comparison. Pro passes 21/50 versus 94/100;
Flash passes 18/50 versus 90/100, and Luna passes 20/50 versus 82/100.
Of the 28 all-fail tasks, 22 belong to this 50-task cohort. Thus this construction
cohort concentrates difficult observed cases. This cohort is distinct from the additional
50 tasks used only in the extended evaluation.

The saved logistic model uses all 900 outcomes, model indicators, construction
cohort, and lift type, with standard errors clustered by task ID. The
construction-cohort odds ratio is 0.149 ($p=1.07\times10^{-7}$).
These are associations in the curated, frozen collection, not effects of a
randomized task-construction intervention.

\paragraph{Lift type describes structure, not an independent difficulty ordering.}
The unadjusted Direct--Adapted--Composite gradient is confounded with cohort
composition: 15 of 18 Composite tasks belong to the later cohort, whereas
53 of 56 Direct tasks belong to the other 100-task cohort. After controlling
for model and construction cohort, Composite versus Direct has odds ratio
0.655 ($p=0.486$) across six configurations. The corresponding Pro/Flash/Luna
analysis gives 0.654 ($p=0.554$); Adapted is also nonsignificant in both analyses.
We therefore do not interpret lift types as an independent difficulty scale.
Figure~\ref{fig:coverage} describes benchmark composition, and
Appendix Table~\ref{tab:structure} retains category-wise outcomes for reference.

\section{Diagnostic Analysis and Discussion}
\label{sec:diagnostics}

The quantitative results establish what happened under the recorded protocol.
This section uses artifact cases to examine incomplete behavior recovery and
derives implications for future agents and benchmark design.

\subsection{Exploratory Evidence on Behavioral-Contract Recovery}
\label{sec:cases}

We inspect public contracts, first-failure evidence, submitted implementations,
and source-access evidence to study incomplete behavioral recovery. We use
\emph{contract-closure gap} as a descriptive term for a delivered artifact
that omits or changes required observable behavior despite implementing a
substantial part of the target. A Hidden failure alone is insufficient for this
label: the failed expectation must first be supported by the public contract.

We develop two cases from the saved artifact failures: dependency-group parsing
in \texttt{poetry-core} and environment discovery in \texttt{tox}. For each task,
we separately inspect Pro's and Flash's saved implementation, the declared
behavior, and the recorded first failure. All four artifacts pass Build and
Isolation but fail Public. These are purposively selected illustrations of
observable mismatches, not a representative sample for estimating their
frequency. The descriptions below use public obligations and submitted code;
they do not reproduce protected test inputs or assertions.

\paragraph{Case 1: an implemented parser covers only part of the input contract.}
The dependency-group task requires
\texttt{parse\_project\_dependencies} to construct \texttt{DependencyGroup}
objects from PEP~621 project metadata (B001). It also requires a mapping-based
\texttt{dependency-groups} representation and transitive group inclusion (B002),
with circular includes raising \texttt{ValueError} (B003). These obligations
jointly define the task's accepted input boundary; supporting group inclusion
does not remove the project-metadata requirement.

Both artifacts expose the requested data classes and parser/resolver functions.
Their group resolvers traverse include references and contain cycle checks.
The mismatch occurs earlier, when input is converted into group objects. Pro's
parser begins with
\texttt{project.get("dependency-groups", \{\})}, iterates the resulting mapping,
and returns the constructed groups. It has no corresponding path for project
dependencies or optional dependencies. Flash accepts additional spellings or
nesting of the group mapping, but similarly returns an empty mapping when that
representation is absent. The recorded Public failures show an empty parser
result on project-metadata input, before downstream group resolution can supply
the missing behavior.

The result is a partial implementation behind a plausible public API. There is
code for dependency objects, requirement parsing, and recursive resolution, but
the required input family does not reach those components. This is why we retain
the existing behavioral-drift coding while grounding this example specifically
in B001: the function exists, yet its accepted input boundary is narrower than
the declared one. An engineering response would be to trace each declared input
form through parsing, object construction, and resolution, rather than treating
the presence of those functions as evidence that every input form is supported.

\paragraph{Case 2: an existing expansion helper is bypassed by the exported API.}
The \texttt{tox} task requires \texttt{find\_envs} to discover the deterministic
environment names described by brace and factor expressions (B001 and B003).
The package separately exposes factor expansion and environment-specific line
filtering. The required environment-discovery behavior therefore includes a
standalone expression; it is not limited to a conditional configuration line.

Both submitted \texttt{find\_envs} functions iterate over
\texttt{expand\_factors(value)} and collect names only when the returned factor
component is non-null. Their \texttt{expand\_factors} implementations identify
factors through a colon separator followed by whitespace or the end of a line.
Without that separator, the line is treated as ordinary content and its factor
component remains null. Consequently, a standalone brace expression contributes
no names. The saved Public failures record the resulting empty collection.

The implementations also contain a lower-level \texttt{find\_factor\_groups}
path and brace-expansion code using a Cartesian product. Thus, the visible
problem is not the wholesale absence of an expansion implementation: the
exported discovery function routes this required input through a parser for a
different input context and skips it before the expansion path is reached.
This static call-path explanation is supported independently in both artifacts;
it does not require inferring what either agent intended. It also shows why
helper presence or successful import is insufficient evidence of end-to-end
behavior preservation. Verification needs to start at the exported API and
follow the requested input through the composed implementation.

\paragraph{What the cases establish.}
The two cases expose distinct ways to narrow a contract inadvertently: omitting
an accepted input representation, and selecting an internal path whose
precondition excludes a required input. Both produce an empty result despite
substantial implementation content. An empty result alone would not distinguish
these explanations from a missing resource, an incorrect registry, or a
specification problem; the contract and code are needed to make the distinction.
The cases support examining behavior across API boundaries and call paths.
They do not establish that every failure shares this structure, or that any
particular prompting or verification intervention would prevent it.

The cases involve source-backed implementations, but repository access does
not establish that every relevant dependency was located or understood.
The analysis concerns observable artifact symptoms rather than a causal
decomposition of search, reasoning, and editing. We do not report independent
inter-rater agreement for the qualitative interpretation.
The accompanying case index described in Appendix~\ref{app:diagnostic-counts}
records the four selected artifacts and their implementation locations.

\subsection{Implications for Feature-Lifting Agents}
\label{sec:discussion}

The results suggest changes to what agents verify and what evaluations report.
The following directions are motivated by the observed artifacts and campaign
outcomes; their effectiveness has not been tested in this study.

\paragraph{Track obligations through the exported interface.}
RQ2 shows that Pro and Flash deliver packages for every task and have no
Build-first failures, yet 76 of their 77 combined failures first appear in a
behavioral test group. The cases in Section~\ref{sec:cases} explain why checking
exports alone can leave substantial obligations unverified. In the parser case,
a required input form never becomes a group object; in the expansion case,
relevant helper code exists but is bypassed by the public entry point. This
motivates tracing a public clause through its input conditions, implementation
path, and observable result. For an agent, the corresponding work belongs both
in planning and in final verification: identify the distinct input forms and
cross-operation interactions, then probe them through the submitted package's
exported interface. Such probes can be derived from the public contract without
access to benchmark tests. Whether a structured obligation record or additional
probing improves success remains an empirical question.

\paragraph{Verify the delivery boundary separately from semantic coverage.}
The four case artifacts pass the recorded Build and Isolation gates, so their
specific mismatches persist after a package has been produced and loaded without
the source repository. Conversely, the full campaign includes missing submissions and
loading failures, which require different diagnoses from an incorrect parser
result. A feature-lifting workflow should therefore collect the deliverable,
load it in its permitted dependency environment, and exercise its public API
there. A source-free verification environment can expose assumptions about local
paths, implicit imports, and resources that an in-repository check may retain.
This recommendation follows the task boundary, not a claim that isolation is
the dominant remaining bottleneck. RQ2's four Isolation-only residuals show only
that the explicit gate rarely decides the result after all other gates pass;
source dependence can already fail during loading or behavioral execution.

\paragraph{Report artifact footprint conditional on functional success.}
RQ4 finds substantial differences on matched successful tasks: for the 97 tasks
passed by both Pro and Luna, median reference-relative size is 0.993 versus
0.697, while median detected copy fraction is 0.966 versus 0.191. Fixing task
membership makes these differences informative about delivered artifacts,
although it does not establish their downstream maintenance cost. Evaluation
should retain functional success as a prerequisite and report relative size and
copying as separate properties of successful outputs. For agent design, this
suggests separating behavior preservation from subsequent footprint reduction:
a candidate reduction would need renewed contract checks before its smaller
size could count as an improvement. Neither a low copy fraction nor a small
artifact alone establishes faithful extraction, and the frozen reference is a
comparison point rather than a proven minimum implementation.

\paragraph{Use observed task variation to guide diagnosis.}
RQ3 identifies a strong construction-cohort association and shows why the
unadjusted lift-type gradient should not be treated as an independent finding.
These comparisons and task solve frequencies can guide case selection without
presuming that a construction label explains a failure. Future diagnostic samples should
span the observed solve-frequency range and the requested behavior types.
The two cases here illustrate input and call-path gaps; they do not establish
their prevalence across the benchmark. Frequency guides what to inspect,
while contract and artifact evidence must explain the implementation mismatch.

\paragraph{Preserve the link between contracts and scores.}
Benchmark maintenance should version contracts, tests, source evidence, and
execution conditions together. Reference replay establishes feasible execution;
semantic review checks whether the evaluator measures the declared behavior.
These complementary checks support interpreting an agent's score and reproducing
its evaluation under the same task definition.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct validity.}
Finite behavioral tests cannot prove equivalence to every behavior of an upstream
feature. The output contract deliberately covers a bounded capability, and
passing should be interpreted within that scope. Contract/evaluator disagreements can misclassify agents even with author
review and reference execution; neither provides a proof of complete test validity. Build allows path loading
and therefore does not prove wheel validity or clean installability. Isolation
is also an operational check: dependency mistakes may surface at other gates,
and the environment's available packages can mask undeclared dependencies.

\paragraph{Internal validity.}
The common comparison fixes task membership and information access and
uses a shared agent/evaluator image pair. Outcomes also depend on the
model--harness configuration: Pro/Flash use different condenser settings from
the other backends, and provider behavior and tool-call compatibility can
affect execution. Score differences therefore characterize the evaluated
configurations rather than the effect of changing the model alone.
Preflight replacement and transient recovery are part of the collection
procedure; reproductions should preserve this procedure alongside the task
definitions, dependency environment, and agent settings.

\paragraph{External and statistical validity.}
The task set emphasizes Python libraries and developer tooling. It does not
establish results for other languages, interactive applications, distributed
services, or industrial migration workloads. Popular source projects may have
appeared in training data; source availability is intentional, while training
contamination is not measured. Observed solve frequencies depend on the
evaluated configurations and this curated collection. A single outcome per cell
does not estimate sampling variation across repeated runs. Reported task-level
intervals and exploratory tests also do not fully account for shared repository
origins or multiple comparisons.

\paragraph{Annotation and footprint validity.}
Task packages received author review supported by AI-assisted checks. Author
involvement in construction can introduce confirmation bias. The qualitative
cases are purposively selected, and we do not report independent inter-rater
agreement or a representative six-configuration causal taxonomy. Repository access is
not proof of successful localization. RRES depends on the feasible reference
and line-counting convention, and direct-copy detection is a syntactic proxy.
Neither metric establishes minimality, maintainability, or semantic superiority.


\section{Related Work}
\label{sec:related-work}

We position feature lifting along four dimensions: the implementation evidence
available to the agent, the behavior it is asked to deliver, the environment in
which that deliverable is evaluated, and the properties measured after success.
These dimensions connect \flb to software reuse research while distinguishing
its task from issue resolution and feature development.

\subsection{Slicing, Feature Location, and Software Reuse}

Program slicing retains statements relevant to a specified slicing
criterion through dependence analysis~\cite{weiser1984slicing}. Feature location
asks which source entities implement a concern, with techniques drawing on
different forms of static, dynamic, and textual
evidence~\cite{dit2013featurelocation}. Separation-of-concerns research studies
decomposition when concerns overlap across a module
hierarchy~\cite{tarr1999degrees}. These lines of work explain why recovering a
capability may require reasoning across several implementation regions.
They also provide possible techniques for agents solving \flb tasks.
Our evaluation target is the delivered package: locating relevant code is useful
only insofar as the resulting artifact satisfies the declared behavior on its own.

Automated software transplantation is a close antecedent. Barr et~al. use
lightweight annotations, analysis, testing, and search to extract donor
functionality and integrate it into a host~\cite{barr2015transplantation}.
Their formulation already treats preservation during extraction as an
executable objective. \flb evaluates repository agents under a different
interface: the source repository and output contract are supplied, source-location hints
are withheld, and the destination is a standalone package rather than a supplied
application integration site. It leaves extraction strategy open, including
behaviorally compatible reimplementation. The benchmark measures satisfaction
of finite obligations and artifact footprint, without asserting semantic
equivalence to the entire source repository or minimality of the extracted program.

This relationship also shapes the evaluation criteria. A source slice is not a
required answer, and similarity to one implementation does not define functional
success. Multiple packages can meet the same contract. Reference-relative size
and detected copying characterize those packages after behavioral evaluation;
they do not establish that a smaller package is easier to maintain or that a
rewrite is preferable to faithful reuse.

\subsection{Executable Coding and Feature-Development Benchmarks}

HumanEval evaluates function synthesis from docstrings through execution
tests~\cite{chen2021codex}. SWE-bench instead supplies an issue and a repository
snapshot, then evaluates a proposed patch in the revised
project~\cite{jimenez2024swebench}. Its issues can include feature requests as well
as bug reports. SWE-Bench Pro extends issue-oriented evaluation toward
longer-horizon changes, augments task descriptions with requirements and relevant
interfaces, and examines agent failures~\cite{deng2025swebenchpro}.
These benchmarks motivate executable repository tasks and explicit requirements;
their requested outcome remains a change to the target project.

Feature-development benchmarks are particularly relevant. FeatBench supplies
natural-language requirements and a base-commit repository, withholding code
hints such as file paths and signatures~\cite{chen2026featbench}. FeatureBench
specifies callable interfaces and constructs tasks by removing target
functionality. Its L1 setting retains the incomplete repository, whereas L2
removes the repository during inference and requests construction from
scratch~\cite{zhou2026featurebench}. Accordingly, standalone feature construction
is already covered by prior work. Our question concerns the agent's use of the
intact implementation as evidence for a new artifact, under an execution
boundary that removes the source repository from the submitted package's runtime.

Table~\ref{tab:positioning} compares these task interfaces. In \flb, exposing the
complete source repository is intentional: it makes source-backed reuse the object of
measurement. The output API fixes the client's expected interface, while
source-location hints remain absent. This is a different information choice
from FeatBench's omission of code-level interface hints. The comparison concerns
what each evaluation asks an agent to do; scores from different task collections
do not establish which setting is intrinsically harder.

\flb combines access to source implementation evidence, a bounded preservation
contract, and evaluation of an independent package. The resulting measurements
address two aspects of reuse: whether the artifact works, and what implementation
it retains. The source project is a reference for understanding behavior during
construction; it is not a runtime dependency available to the submitted artifact.

\subsection{Agent Runtimes and Evaluation Scope}

SWE-agent studies interfaces through which language models navigate repositories,
edit files, and execute tests~\cite{yang2024sweagent}. OpenHands supplies an
extensible platform for developer agents with sandboxed tool
execution~\cite{wang2025openhands}. Harness-Bench directly examines variation
across model--harness configurations under shared tasks and
budgets~\cite{yao2026harnessbench}. These studies motivate reporting the harness
and its context-handling policy as part of the evaluated system. Our experiments
use OpenHands to instantiate the feature-lifting task; the results characterize
the recorded configurations rather than establishing a harness-independent
ordering of models.

Terminal-Bench evaluates diverse command-line tasks using task-specific
environments and executable verification, with separate discussion of
construction, validation, difficulty, and error
analysis~\cite{merrill2026terminalbench}. OSWorld supports computer tasks with
explicit initial-state setup and execution-based evaluation across desktop
applications~\cite{xie2024osworld}. They provide broader settings for agent
interaction, while \flb focuses on the boundary between a source repository and
a reusable software artifact. Their treatment of environments and verification
also motivates separating our source provenance, reference execution evidence,
and semantic task-validity discussion. Repeatable execution and fair behavioral
expectations are related requirements that need different supporting evidence.

\section{Conclusion}

\flb asks whether a coding agent can preserve an existing capability while
moving it across a new package boundary. Its 200 Python tasks span 176
repositories and 182 source snapshots. Complete source evidence and explicit
contracts define the task; source-free execution tests the resulting artifact.
Automated checks, AI-assisted review, author review, and repeated
reference execution provide complementary validation evidence.

In the primary comparison of six configurations on the same 150 tasks,
functional pass rates range from 24.0\% to 76.7\%; five configurations also
cover the remaining 50 tasks. Strong agents deliver packages reliably, but
76 of the 77 combined Pro/Flash failures first occur at behavioral gates.
The apparent lift-type gradient is explained in part by construction-cohort
composition; it is not an independent difficulty finding. Concrete failure
cases show how required behavior is lost during adaptation or reconstruction.
Artifact and efficiency measurements characterize successful implementation
size, direct source overlap, and observed execution effort. Together, these results position
behavior preservation across software boundaries as a distinct challenge for
coding agents and establish a benchmark for studying reliable feature reuse.

\paragraph{Detailed configuration.}

task timeout.

\paragraph{Paired comparison statistics.}
The paired copying comparisons in Table~\ref{tab:paired} use 97 common passes

($p=4.24\times10^{-13}$, $r=0.885$). These Wilcoxon tests and rank-biserial
effect sizes concern copying, not RRES.

\paragraph{Task-level evidence.}
The main result matrix contains 900 rows indexed by configuration and task ID.

trajectories, configuration metadata, and usage records. The additional
50-task results are read from the corresponding five configurations' saved
evaluator outputs. Paired statistics and task-composition summaries retain
their task membership so that denominators can be checked directly.

The saved consistency checks compare initial prompts, dependency locks,

Upstream snapshots retain their original licenses. Source acquisition,
evaluator assets, and submitted artifacts are kept separately to preserve
their respective licensing and information-access requirements.


\subsection{Delivery and Interaction Records}

Process evidence helps interpret failed delivery. Qwen's 25 empty
submissions are associated with tool-validation failures involving required
tool-call fields. GLM's 38 empty submissions are predominantly early terminations
without a package; only one is tagged as a tool-validation event. These are
different model--harness outcomes and should not be pooled into behavioral
failure categories. Conversely, 82 Flash passing artifacts have runner status
other than passed, illustrating why workflow status cannot replace evaluation.

Provider token accounting is incomplete and heterogeneous. Luna and GLM lack
verified token totals for this analysis. Pro and Flash expose cache accounting,
allowing an incremental measure of uncached prompt plus completion tokens;
their overall medians are approximately 88.0k and 123.6k. Qwen and OSS have
provider total-token counts without the same cache breakdown. We therefore
do not rank all six backends by token cost.
