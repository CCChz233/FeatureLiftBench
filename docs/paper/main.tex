\title{FeatureLiftBench: A Benchmark for Behavior-Preserving Feature Lifting Across Software Boundaries}
\author{Anonymous Author(s)}
\begin{abstract}
Software reuse is a fundamental software engineering practice involving the adaptation and integration of existing functionality into new systems. For coding agents, such reuse requires reconstructing existing capabilities across software boundaries while preserving their behavior.
Yet existing coding-agent benchmarks largely focus on
modifying repositories or generating functionality from specifications, leaving this cross-boundary form of software reuse underexplored.
To address this gap, we introduce \emph{behavior-preserving feature lifting}, a reuse setting in which a coding agent rebuilds an existing capability from a source repository as an independent package that must satisfy a behavioral contract without runtime access to the source.
We instantiate feature lifting in FeatureLiftBench, a benchmark of 150 Python tasks from 126 real-world repositories that combines intact source repositories, explicit behavioral contracts, and source-free evaluation. Across six model--harness configurations, pass rates range from 24.0\% to 76.7\%.
Repository evidence raises pass rates by 32.0--56.0 percentage points over a contract-only condition, yet a mechanical relocation baseline passes only 20.7\% of tasks, and 79.5\% of behavioral failures occur after the agent has read the relevant source.
Manual review of these failures reveals recurring mismatches in ambient assumptions, supporting representations, and destination-specific adaptations. Feature lifting is therefore not merely a localization or copying problem: successful reuse requires translating source evidence into behavior that remains correct across a new package boundary.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Software reuse involves selecting, adapting, and integrating existing
artifacts~\cite{krueger1992reuse}. Moving a capability across project boundaries
is one such reuse scenario: a developer may need a parser from a larger tool,
configuration handling from a framework, or a signal registry for a new library.
An implementation that works within its source repository may depend on
supporting modules, shared state, framework mechanisms, configuration, or
resources that do not automatically cross a new package boundary. Software
reuse therefore requires more than locating an apparent entrypoint: the
supporting assumptions and behavioral relationships that make a capability work
must also be reconstructed. Existing repository-level coding benchmarks mainly
focus on repairing existing systems or implementing new functionality, leaving
the reconstruction of existing capabilities across package boundaries
underexplored. We therefore ask: \emph{when coding agents rebuild an existing
capability as an independent package, with its original implementation at hand,
which behaviors do they fail to preserve, and why?}

We formulate this task as \emph{behavior-preserving feature lifting}, or
\emph{feature lifting} for short. Throughout, a \emph{feature} is an existing
capability of a source project whose behavior is observable through an API.
Given a version-pinned source repository and a public behavioral contract, an
agent builds a new package that is then evaluated without runtime access to the
source repository. The agent may copy, adapt, or reimplement upstream code; what
matters is the behavior of the result. A lift succeeds if the new package
satisfies the contract, which specifies the upstream behavior to retain together
with any declared adaptations. The source repository thus serves only as
evidence during construction: any supporting code, state, or resources that the
capability needs at runtime must be rebuilt inside the new package.
Figure~\ref{fig:pipeline} illustrates this setting.

This setting differs from several closely related repository-level coding
settings. SWE-bench and SWE-Bench Pro ask agents to modify an existing project
in response to an issue~\cite{jimenez2024swebench,deng2025swebenchpro}, while
FeatBench and FeatureBench study feature implementation in an existing,
partially removed, or specification-driven codebase~\cite{chen2026featbench,zhou2026featurebench}.
Classical software transplantation moves donor functionality across project
boundaries, but integrates it into a supplied host program rather than producing
a standalone package~\cite{barr2015transplantation}.

Table~\ref{tab:setting-comparison} summarizes these distinctions. Repository
repair and in-repository feature development retain the original project as the
execution context. Specification-driven standalone construction, as in
FeatureBench L2 and RepoZero~\cite{zhou2026featurebench,zhang2026repozero}, can
produce an independent artifact, but does not expose the intact source implementation as
construction evidence. Software transplantation has access to donor source and
crosses a project boundary, but targets integration into a supplied host.
Feature lifting combines these otherwise separate properties: the intact source
implementation remains available as evidence during construction, but the
original execution context is removed. The agent must therefore rebuild the
capability so that it satisfies the contract inside its new package, not merely
relocate upstream code into another project.

To study this problem, we introduce \flb, a validated benchmark of
150 Python tasks constructed from capabilities in 126 real repositories.
Unlike benchmarks that can be automatically mined from issue reports, feature
lifting tasks require explicit behavioral contracts, protected tests, and
source-independent reference packages. Therefore, we
prioritize validated task quality and behavioral coverage over large-scale noisy
collection. The benchmark is validated through automated consistency checks, manual semantic review of
contracts and tests, and repeated source-free reference execution.

We organize our study around three research questions:
\begin{itemize}
  \item \textbf{RQ1:} How does feature-lifting success vary across agent
  configurations and task structures?
  \item \textbf{RQ2:} Does repository evidence improve feature lifting, and can
  its benefit be explained by mechanical source relocation?
  \item \textbf{RQ3:} What implementation mismatches remain in behavioral
  failures that occur after the agent has read the relevant source?
\end{itemize}
Across six model--harness configurations, pass rates range from 24.0\% to
76.7\% (RQ1). Removing the repository lowers pass rates by 32.0--56.0
percentage points in all three configurations tested, yet a mechanical
relocation baseline passes only 20.7\% of tasks (RQ2). Moreover, 79.5\% of
behavioral failures, i.e., runs whose package loads but fails the protected
behavioral tests, occur after the agent has read source files associated with
the requested entrypoints. In a manual review of 40 such failures, we observe
recurring cases in which the agent preserves the central logic but mishandles an
ambient assumption such as the executing platform, a supporting data
representation, or an adaptation that only the destination requires (RQ3). Feature lifting is therefore not a
localization or copying problem: the agent must rebuild behavior that remains
correct under a new package boundary.

This work makes three contributions:
\begin{itemize}
  \item \textbf{A task formulation for behavior-preserving feature lifting.}
  We define a repository-level reuse setting in which agents rebuild an existing
  capability as an independent package. The intact implementation is available
  as evidence during construction, but correctness is judged solely against the
  destination contract.

  \item \textbf{FeatureLiftBench, an executable benchmark for feature lifting.}
  We construct and validate 150 tasks from 126 real Python repositories, with
  explicit behavioral contracts, protected tests, source-free evaluation, and
  executable reference packages.

  \item \textbf{A diagnosis of feature-lifting failures.}
  Paired ablation, trajectory analysis, and manual review show that failures
  often persist after the agent has read the relevant source, and reveal
  recurring mismatches in ambient assumptions, supporting representations, and
  destination-specific adaptations.
\end{itemize}

\section{The FeatureLiftBench Benchmark}
\label{sec:benchmark}

\subsection{Task Formulation and Running Example}
\label{sec:formulation}

A \flb task consists of a pinned source repository $R$ and a public behavioral
contract $S$. From $S$, we derive a task statement $P$ that states the same
target APIs and behavioral requirements and also explains the workspace. The
agent receives $P$, but not the structured contract $S$, protected tests, or
source-location hints. The workspace contains $P$, metadata identifying the
upstream repository, destination package, and permitted environment, a
dependency lock file, an empty submission directory, and a copy of $R$. The
repository copy is omitted only in the Contract Only ablation
(Section~\ref{sec:source-ablation-protocol}). A model backend $M$ acting
through an agent harness $H$ produces the submitted package $A$:
\begin{equation}
  A = \operatorname{Run}(M,H,R,P),
\end{equation}
which an independent protected evaluator then judges.

A feature-lifting contract defines the behavior required of the new
package~\cite{meyer1992contract}. It may contain three kinds of requirements:
upstream behavior to retain, declared adaptations that permit or require
differences from upstream behavior, and obligations that arise only in the
destination package. Behavior preservation refers to the first kind. The
contract makes the API surface, relevant defaults, exceptions, state changes,
ordering constraints, and exclusions explicit. The agent may inspect the
complete pinned repository, including upstream tests and documentation, but
must submit the result as the package \texttt{featurelifted}. Task metadata also
records \emph{entrypoints}, the upstream symbols that implement the requested
capability. This mapping is used only for offline analysis and the DSE baseline
(Section~\ref{sec:rq2}) and is hidden from the agent, together with the
benchmark tests, reference packages, and test-to-contract mappings.

The required output is a package that executes in the benchmark environment
without runtime access to the source repository. Because the contract constrains
behavior rather than structure, structurally different implementations can
satisfy the same task.

Functional success is defined as
\begin{equation}
  F(A)=B(A)\land T_{\mathrm{primary}}(A)
       \land T_{\mathrm{extended}}(A)\land I(A),
  \label{eq:functional}
\end{equation}
where $B$ checks that the submitted package can be loaded under the frozen
evaluation environment, $T_{\mathrm{primary}}$ and
$T_{\mathrm{extended}}$ run the protected Primary and Extended tests, and $I$
checks source independence. All four conditions must hold.

\paragraph{Running example: a signal registry.}
The Blinker task asks the agent to reconstruct \texttt{Signal} and
\texttt{Namespace} under a new package boundary. Its contract requires behavior
such as sender-specific dispatch, weak-receiver cleanup, stable namespace
identity, and scoped connection management, while explicitly excluding
asynchronous dispatch and the upstream global named-signal singleton. Thus, an
implementation whose central \texttt{connect} and \texttt{send} paths work can
still fail if supporting state or lifetime behavior is lost. Whether the agent
reuses or reimplements the upstream logic, the resulting package must satisfy
the contract without importing or reading the original \texttt{blinker} source
at runtime.

\subsection{Task Construction}
\label{sec:construction}

Figure~\ref{fig:construction} summarizes the construction and validation
workflow.
\paragraph{Select a capability and pin its source.}
We select capabilities from Python libraries, developer tools, and framework
components when their observable behavior can be stated explicitly and executed
without live external services. Each task is tied to a pinned source snapshot.
The complete tracked source tree is retained, leaving source localization and
dependency recovery to the agent.
Candidate tasks that could not be specified, evaluated, or validated under this
protocol were excluded before the benchmark was frozen.

\paragraph{Define the behavioral contract.}
For each capability, we specify the APIs and observable requirements described
in Section~\ref{sec:formulation}, including any declared adaptations and exclusions.
The resulting task statement prescribes destination behavior without
source-location hints or implementation instructions.

\paragraph{Construct protected tests and a reference package.}
Primary and Extended test groups operationalize the same public contract:
Primary covers central obligations, while Extended exercises additional cases
and combinations without introducing new requirements. Both groups are hidden
from the agent. Test-to-contract mappings are maintained during construction to
check that evaluator expectations remain within the contract.

For each task, we also retain a reference package that passes the same
source-free functional evaluation as agent submissions. Reference packages may
be constructed by extracting and adapting upstream code or by task-specific
implementation. They establish that the task is executable under the benchmark
environment and provide a reference point for artifact-size measurements;
they are not necessarily unique or minimal implementations.

\paragraph{Freeze the benchmark.}
After validation, task specifications, pinned source identities, protected
tests, reference packages, dependency policies, and evaluator settings are
versioned together. Every configuration in the main comparison is evaluated on
the same 150 tasks.

\subsection{Benchmark Validation}
\label{sec:validation}

Validation must address whether evaluator judgments capture the intended
behavior, an instance of the test-oracle problem~\cite{barr2015oracle}.
We validate the frozen benchmark at three complementary levels: structural
consistency, semantic alignment, and executable feasibility.

\paragraph{Structural consistency.}
Automated checks verify required task assets, source mappings, dependency
declarations, generated task statements, and test-to-contract mappings. All 150
retained task packages pass these checks and resolve to 132 verified source
snapshots. These checks target inconsistencies such as stale specifications,
missing API declarations, and invalid test mappings.

\paragraph{Semantic alignment.}
We first ran an AI-assisted, task-level review of every task package in Cursor
and Codex, checking benchmark quality and whether each task statement aligned
with its protected tests. This review supported the authors rather than serving
as a semantic judge. All 150 retained tasks were subsequently
manually reviewed by the authors for consistency among the public contracts,
protected tests, pinned-source evidence, explicit exclusions, and taxonomy
labels. Final retention and correction decisions were made by the authors.

\paragraph{Executable feasibility.}
Each retained reference package is replayed three times under the same
source-free functional evaluation used for submissions. All 450 executions
(150 tasks $\times$ 3 runs) pass. Reference replay therefore establishes that
every frozen task admits at least one executable solution under the benchmark
environment; it does not by itself establish semantic completeness, which is
addressed separately by contract and test review.

\subsection{Dataset Composition}
\label{sec:suite}

We characterize the 150 tasks along three complementary dimensions:
\emph{functional family} describes what capability is lifted, \emph{lift type}
describes how the requested capability relates to its upstream implementation,
and \emph{entanglement} describes which forms of project dependency must be
handled when crossing the new package boundary. These annotations describe
benchmark composition and do not affect scoring.

\paragraph{Functional coverage.}
The benchmark spans ten functional families across 126 repositories and 132
pinned source snapshots; some repositories are pinned at more than one version. The largest families are parsing/tokenizing/decoding
(31 tasks), registry/plugin dispatch (22), serialization/formatting/rendering
(19), configuration resolution/discovery (18), and
validation/normalization/construction (15). The remaining tasks cover workflow
and session orchestration, resource and metadata loading, algorithms and data
structures, protocol state transitions, and cache/retry policies.

\paragraph{Lift types.}
Each task receives one of three labels according to the relation between the
requested capability and its upstream implementation. \emph{Direct} tasks
require an identifiable upstream capability to be preserved outside its original
project. \emph{Adapted} tasks retain an identifiable capability but require a
declared change to its interface or observable behavior.
\emph{Composite} tasks combine multiple upstream capabilities or reconstruct a
workflow without a single corresponding upstream API. The benchmark contains 56
Direct, 76 Adapted, and 18 Composite tasks. These labels characterize the
requested transformation rather than the implementation strategy used by an
agent.

\paragraph{Entanglement mechanisms.}
Tasks may additionally carry multiple labels describing the dependencies that
must be accounted for during lifting. We group the underlying annotations into
four mechanisms: \emph{code dependencies}, covering internal helpers, transitive
imports, and third-party interfaces; \emph{data and state}, covering shared
models, parser state, and registries; \emph{framework mechanisms}, covering
lifecycle, dispatch, and dynamic discovery; and \emph{environment and
resources}, covering configuration, path rules, and packaged resources. These
mechanisms are non-exclusive and describe where a capability is coupled to its
source project.

Figure~\ref{fig:coverage} summarizes the resulting composition. Panel~(a) shows
the ten functional families partitioned by lift type, while panel~(b) shows the
prevalence of the four entanglement mechanisms overall and within each lift
type.



\section{Evaluation Protocol and Experimental Setup}
\label{sec:protocol}

\subsection{Agent Configurations}

We evaluate DeepSeek V4 Pro (\texttt{deepseek-v4-\allowbreak pro-0813}), DeepSeek V4 Flash
(\texttt{deepseek-v4-\allowbreak flash-0731}), GPT-5.6 Luna, GLM-5.3-Flash,
Qwen3.6-35B-A3B, and GPT-OSS 120B, abbreviated as Pro, Flash, Luna, GLM,
Qwen, and OSS. All configurations use OpenHands CLI 1.16.0 with native tool
calling~\cite{wang2025openhands} and follow the information boundary defined in
Section~\ref{sec:formulation}.

Every run in the main comparison and paired ablation uses a 3,600-second timeout,
a 131,072-token context window with 8,192 tokens reserved for output, and a
maximum of 150 steps. Agents have no network access during construction.
Remaining runtime settings follow the OpenHands configuration recorded for each
model, which is provided in the replication materials. Work on
agent--computer interfaces and harness
effects motivates reporting these execution choices as part of the evaluated
system~\cite{yang2024sweagent,yao2026harnessbench}. We therefore treat each
model--harness configuration as the experimental unit rather than attributing
observed differences to the base model alone.

\subsection{Functional Evaluation and Artifact Metrics}
\label{sec:functional-eval}

Only the collected submission enters the evaluator environment; the source
repository is unavailable at runtime, networking is disabled, and dependencies
are fixed. Functional success follows Equation~\ref{eq:functional}. The
\textbf{Build} gate checks that the submitted package can be loaded under the
frozen evaluator environment; \textbf{Primary} and \textbf{Extended} use protected
tests to exercise behavioral obligations specified by the same public contract; and
\textbf{Isolation} checks that the package neither depends on the original
repository nor accesses evaluator-private paths, such as task definitions,
source snapshots, and reference packages. We classify each unsuccessful run by its first failed gate in the order
Build, Primary, Extended, Isolation, and call runs that first fail at Primary or
Extended \emph{behavioral failures}.

\paragraph{Successful-artifact characteristics.}
For a functionally passing artifact $A$ and its reference package
$A_{\mathrm{ref}}$, we define Reference-Relative Extraction Size as
\begin{equation}
  \operatorname{RRES}(A)=
  \frac{\operatorname{PythonLOC}(A)}
       {\operatorname{PythonLOC}(A_{\mathrm{ref}})}.
  \label{eq:rres}
\end{equation}
RRES characterizes artifact size relative to one reference package, not
minimality.

We additionally report \emph{Copy}, the fraction of submitted Python source
matched to the source repository in normalized sequences of at least three
consecutive non-empty, non-comment lines. Copy measures syntactic overlap rather than semantic
equivalence, a distinction established in code-clone
research~\cite{roy2009clones}, and can miss rewritten equivalents.
Both metrics are computed only for functionally successful artifacts and do not
affect the functional score: a lift succeeds by satisfying the contract and
source independence, while RRES and Copy describe how compactly and how directly
it reuses the source implementation.

\paragraph{Execution effort.}
Table~\ref{tab:main} reports the number of recorded steps and total token
usage for all assigned tasks. Total tokens per run are input tokens, including
cached input, plus output tokens (Section~\ref{sec:execution-effort-protocol}).

\subsection{Comparison Scope and Statistical Analysis}
\label{sec:statistics}

The main comparison evaluates six configurations on the same 150 tasks, with
one run per task--configuration pair. All assigned tasks remain in
the denominator, including runs that produce no usable submission. Pass rates
therefore describe the observed performance of the evaluated model--harness
configurations and do not capture run-to-run variance.

The repository-evidence ablation compares Full Source and Contract Only on the same
tasks using paired pass-rate differences, paired bootstrap confidence intervals,
and exact conditional McNemar tests~\cite{fagerland2013mcnemar}, with Holm
correction across configurations~\cite{holm1979multiple}. Intervals use
100{,}000 paired task-bootstrap resamples and describe variation across task
pairs rather than repeated agent runs.

We compare successful-artifact footprints using task fixed effects to account
for differing successful task sets. We retain tasks with successful artifacts
from at least two configurations and fit:
\begin{equation}
\begin{aligned}
  \log_2\!\left(\operatorname{RRES}_{t,m}\right)
    &= \alpha_t^{\mathrm{RRES}} + \beta_m^{\mathrm{RRES}}
       + \epsilon_{t,m}^{\mathrm{RRES}}, \\
  \operatorname{Copy}_{t,m}
    &= \alpha_t^{\mathrm{Copy}} + \beta_m^{\mathrm{Copy}}
       + \epsilon_{t,m}^{\mathrm{Copy}},
\end{aligned}
\label{eq:adjusted-footprint}
\end{equation}
with $\sum_m\beta_m^{\mathrm{RRES}}=\sum_m\beta_m^{\mathrm{Copy}}=0$.
Here $t$ indexes tasks and $m$ indexes configurations. Ordinary least squares
gives each successful artifact equal weight. We report the task-adjusted RRES
ratio $2^{\beta_m^{\mathrm{RRES}}}$ and the Copy difference
$100\beta_m^{\mathrm{Copy}}$ in percentage points. Because the configuration
effects sum to zero, a ratio of $1\times$ or a difference of 0\,pp denotes the
average configuration; the ratio is neither an adjusted median nor a raw size
ratio to the reference package.

Pointwise 95\% percentile intervals use task-cluster bootstrap
resampling~\cite{field2007cluster}. Sensitivity checks using task-equal weighting
and repository-level resampling preserve the qualitative results. Resampling
details are provided in the replication materials. As above, the intervals
reflect variation across tasks or repositories, and the analysis is descriptive
and conditional on success.

\subsection{Paired Repository-Evidence Ablation}
\label{sec:source-ablation-protocol}

The paired ablation removes repository evidence while keeping the requested
behavior fixed. We evaluate all 150 benchmark tasks for GPT-5.6 Luna,
DeepSeek V4 Pro, and Qwen3.6-35B-A3B. For each configuration, the
\emph{Full Source} condition uses the corresponding run from the main
comparison, while \emph{Contract Only} uses the same model--harness
configuration on the same task with repository evidence removed. This yields
one task-paired comparison per configuration.

In the \emph{Full Source} condition, the agent receives the complete pinned
repository together with the public behavioral contract. In \emph{Contract
Only}, the repository is omitted while the same contract, the list of permitted
third-party packages, and their locked versions are retained. As in all runs,
the agent has no network access, and retrieving the original project from
installed packages or caches is prohibited. Benchmark tests,
reference packages, and source-location hints remain hidden in both
conditions. The intervention therefore removes repository evidence as a whole,
including source code, upstream tests, documentation, and packaged resources,
rather than isolating source-code text alone.

Within each configuration, the paired conditions use the same model--harness
settings and source-free evaluator. Missing submissions are counted as
functional failures; the paired statistical tests are described in
Section~\ref{sec:statistics}.

\subsection{Trace-Based Source-Exposure Measurement}
\label{sec:source-exposure-protocol}

To distinguish source availability from observable source use, we analyze the
saved trajectories of all 900 runs in the main comparison. For
each task, we map its declared entrypoints
(Section~\ref{sec:formulation}) to files in the pinned repository.

We call an event a \emph{confirmed source read} when a successful tool read
returns content from a file associated with a declared entrypoint. Filename
mentions and failed reads do not count. A run is \emph{source-exposed} if it
contains at least one confirmed source read. Source exposure shows that the
agent saw associated source code; it does not show that the agent located the
complete implementation or understood it.

\paragraph{Qualitative analysis of source-exposed behavioral failures.}
We inspect a fixed, purposively diverse sample of 40 source-exposed behavioral
failures, with one case per task. Selection uses fixed configuration quotas
(seven cases each for Pro, Flash, Luna, and GLM, and six each for Qwen and OSS)
and coverage of functional families and lift types, with
deterministic hash-based tie-breaking. The sample spans all
six configurations, ten functional families, and all three lift types.

Two authors independently reviewed the public contract, pinned upstream
implementation, submitted artifact, and evaluator outcome for each case, and
reconciled disagreements to derive a qualitative coding framework. We then
grouped the cases into non-exclusive themes, each describing how a contract
requirement depends on supporting code relationships and whether that
requirement is inherited from upstream or introduced by an adaptation. Cases
that fit no recurring theme are retained as case-specific observations; the
analysis identifies qualitative patterns, not their prevalence. The replication materials preserve the complete case-to-theme
mapping and review history. Three illustrative cases are paired with successful
artifacts under the same contracts.

\subsection{Retrospective Execution-Effort Analysis}
\label{sec:execution-effort-protocol}

We recover token usage from provider audit logs and persisted per-response
metrics. A parent usage record may already include child calls, for example
OpenHands context-management calls; if the same model response appears in both,
we count it once by response ID after checking that the token counts agree.
Total token usage is computed as the sum of input and output tokens across all
model calls in each run.

For trajectory-level analysis, we reconstruct the submission directory at each
saved tool-completion boundary of a trajectory and evaluate it; the earliest
reconstructed artifact that passes defines the \emph{first passing checkpoint}.
With cumulative tokens $T_r^{\mathrm{pass}}$ at this checkpoint and run total
$T_r$, the post-checkpoint token fraction of run $r$ is
$(T_r-T_r^{\mathrm{pass}})/T_r$. Computing this fraction requires matching every
response ID one-to-one to the event stream, with counts and timestamps that
agree with the audit logs.
We separately count distinct subsequent responses recorded as actions or
messages in the main agent event stream, excluding the response that produced
the passing artifact. This count
excludes harness-internal responses and unobserved HTTP retries. Both measures are
restricted to finally successful runs whose checkpoints could be evaluated and
whose reconstructed final artifact matches the re-evaluated submission. Because
the two measures have different data requirements, they are computed on
different subsets of runs. Values are computed per run before aggregation. The
agent could not observe these checkpoints, so they do not indicate when it could
have stopped.

\subsection{RQ2: Does Repository Evidence Improve Feature Lifting Beyond Mechanical Relocation?}
\label{sec:rq2}
\label{sec:source-ablation-results}

We examine repository evidence from two perspectives: whether access to it
improves feature lifting, and whether its benefit can be reduced to mechanically
relocating existing source code. The first analysis compares Full Source and
Contract Only on all 150 tasks in a paired design. The second compares agents
with a mechanical relocation baseline to examine the limits of direct source
reuse.

\subsubsection{Repository evidence improves feature lifting}

Figure~\ref{fig:source-evidence} visualizes the paired effects, while
Table~\ref{tab:paired-ablation} reports the exact paired statistics.
Repository evidence substantially improves functional success across all three
evaluated configurations. Full Source increases pass rates from 36.0\% to
68.0\% for Luna, from 20.7\% to 76.7\% for Pro, and from 4.7\% to 42.0\%
for Qwen, corresponding to gains of 32.0, 56.0, and 37.3 percentage points,
respectively. All three paired differences remain significant after Holm
correction.

The discordant pairs point in the same direction. For Luna, 56 tasks pass only
under Full Source and 8 only under Contract Only; the corresponding counts are
88 versus 4 for Pro and 59 versus 3 for Qwen. For Pro, 30 Contract Only runs
produce no usable submission, so part of its gain reflects whether any package
is delivered, not only whether the delivered package behaves correctly.

\subsubsection{Mechanical relocation is insufficient}

Repository evidence may benefit agents either by exposing reusable source
implementations or by supporting more complex reconstruction. To distinguish
these possibilities, we introduce Direct Source Extraction (DSE), an
entrypoint-guided mechanical relocation baseline. DSE receives frozen entrypoint
mappings and performs only
predefined relocation operations: source collection, package restructuring,
import rewriting, and frozen symbol-alias exports. An alias export re-exports an
upstream symbol unchanged under the destination name, for example
\texttt{requests\_cache.cache\_keys.create\_key} as
\texttt{featurelifted.create\_cache\_key}. It does not convert arguments, add
logic, or automatically map contract APIs to upstream implementations.
DSE also does not perform semantic modification, test-driven repair, or
task-specific adaptation.
Because DSE receives explicit source-location information unavailable to the
evaluated agents, it serves as a diagnostic baseline rather than a controlled
model ablation.

Across all 150 tasks, DSE passes 31 tasks (20.7\%). Among the 148 tasks for
which DSE produces a submission, the median source overlap with the source
repository, measured with the same matching rule as Copy, is 99.34\%. Despite this near-complete syntactic overlap,
DSE remains substantially below the Full Source results of Qwen (42.0\%),
Luna (68.0\%), and Pro (76.7\%). High source overlap therefore does not, by
itself, ensure functional success under DSE's fixed relocation operations.

DSE success is concentrated in Direct tasks. It passes 22/56 Direct tasks
(39.3\%), compared with 9/76 Adapted tasks (11.8\%) and none of the 18
Composite tasks. This descriptive breakdown shows that mechanical relocation
is most effective when an identifiable upstream capability can be preserved
directly, while its success drops sharply when the requested lift requires
adaptation or composition.

Among the 119 DSE failures, 40 fail first at Build, 55 at Primary, 21 at
Extended, one at Isolation, and two produce no submission. Of the 40
Build-first failures, 25 involve missing upstream dependencies, six involve
missing version modules, seven trigger isolation-related violations during
loading, one retains an upstream-package metadata lookup, and one reflects a
dependency-version incompatibility. These failures show that relocating source
files alone does not automatically reconstruct the dependencies, package
assumptions, and execution context required by an independent package
boundary.

\paragraph{RQ2 Summary.}
Repository evidence substantially improves functional success across all
three evaluated configurations, with gains of 32.0--56.0 percentage points
over Contract Only. Its value cannot be reduced to mechanical source
relocation: DSE achieves 99.34\% median source overlap among generated
submissions but passes only 20.7\% of tasks, with success concentrated in
Direct tasks and dropping sharply for Adapted and Composite tasks. Together,
these results indicate that successful feature lifting requires using source
evidence to reconstruct behavior across the package boundary rather than
simply relocating upstream implementation. This motivates RQ3, which examines
why behavioral failures persist even after the agent has read the relevant
source.

\subsection{RQ3: What Implementation Mismatches Remain in Source-Exposed Behavioral Failures?}
\label{sec:rq3}

We first locate where each unsuccessful run fails. Figure~\ref{fig:failures}
classifies runs by their first failed gate (Section~\ref{sec:functional-eval}), which
shows where a failure becomes observable, not its underlying cause. The figure
shows a clear pattern among the strongest
configurations. Pro and Flash produce usable submissions for all 150 tasks and
have no Build-first failures. Of their 77 combined unsuccessful runs, 76 are
behavioral failures and only one first fails at Isolation. Once these
configurations deliver a package, the remaining obstacle is behavioral
correctness rather than package production or loading.

Weaker configurations exhibit a broader mixture of failure modes. GLM and Qwen
produce no usable submission for 38 and 25 tasks, respectively, while OSS
usually delivers an artifact but has 18 Build-first failures and 93 behavioral
failures. Low pass rates therefore stem from different bottlenecks in different
configurations.

\paragraph{Behavioral failures often persist after source exposure.}
A behavioral failure could arise simply because the agent never inspected the
relevant implementation. The trajectories show that this explanation does not
hold for most runs: 241 of the 303 behavioral failures across the six
configurations (79.5\%) are source-exposed (Table~\ref{tab:source-exposure}),
with the first confirmed read occurring at a median of the fifth tool action. For Pro
and Flash, 63 of their 76 behavioral failures are source-exposed.

Reading source files associated with an entrypoint is therefore not sufficient
for a successful lift. Source exposure cannot explain why an individual run
fails, but it rules out the simple explanation that most behavioral failures
occur before the agent sees any relevant source; the reviewed cases below
examine what goes wrong instead.

\paragraph{Recurring themes across the reviewed sample.}
Across the 40 reviewed cases, we identified three recurring qualitative
patterns:
\emph{changed ambient assumptions}, \emph{incompatible supporting representations
and pipelines}, and \emph{destination-specific obligations requiring adaptation}.
Platform-dependent path helpers in \texttt{platformdirs} and
\texttt{jupyter\_core}, and a construction-time scheduling bound in
\texttt{apscheduler}, illustrate the first theme. Grouped diagnostics in
\texttt{cerberus} and normalization before hashing in \texttt{requests\_cache}
illustrate the second. Resource containment in \texttt{importlib\_resources},
lock-file cleanup in \texttt{filelock}, short-circuit execution in
\texttt{json\_logic}, and configuration parsing in \texttt{python\_decouple}
illustrate the third.

The themes do not exhaust the sample: other cases involve local behavioral
differences, missing members, an artifact constraint, or insufficient evidence
for one of these relationships. We retain them as other or case-specific
observations rather than forcing a theme assignment. The mapping in the replication materials
records every case and reports counts only within this purposive sample.
Figure~\ref{fig:failure-analysis} illustrates one instance of each recurring
theme with a paired failed/successful implementation. Each pair shares the same
archived public contract and pinned source; the successful counterpart passes
all four functional gates.

\paragraph{An explicit input can invalidate an ambient assumption.}
In \texttt{platformdirs}, the destination contract turns platform selection into
an explicit input. The failed artifact selects a Windows branch but still uses
the executing platform's path-joining operations. The successful counterpart uses a
Windows-aware helper for those paths. Selecting the requested branch is therefore
not enough: the helpers below that branch must honor the same platform choice.
The failure lies in adapting an upstream assumption, not in a missing API.

\paragraph{A preserved producer needs a compatible consumer.}
For \texttt{cerberus}, nested validation and diagnostic rendering share a grouped
error representation. The failed artifact produces child and group records,
but its formatter lacks compatible group-aware handling. The successful artifact
connects group production to recursive rendering. Because the contract requires
structured nested diagnostics, preserving the validation logic alone does not
preserve the observable output. Unlike the \texttt{platformdirs} case, the
broken relationship here supports behavior inherited unchanged from upstream.

\paragraph{A destination restriction may require an additional adapter.}
For \texttt{importlib\_resources}, the destination contract requires traversal to
remain within an exposed resource tree. The failed artifact delegates access to
an unguarded resource object; the successful counterpart routes access through
a wrapper that resolves child names within the exposed tree. Containment is a
destination requirement, not an upstream guarantee lost during copying.

In all three pairs, the failed artifact contains the source-backed components,
but their assumptions or interactions no longer match the destination contract.
Checking a lift therefore requires checking how components jointly realize each
contract requirement, and where an adaptation invalidates the assumptions of
reused code.

\paragraph{RQ3 Summary.}
Most behavioral failures (79.5\%) are source-exposed, so they cannot be
explained by missing source inspection alone. In the reviewed sample, recurring
failures arise when reused code keeps an assumption that the destination
changes, when the producer and consumer of a shared representation are not
reconstructed together, or when the destination requires an adapter that the
upstream code never needed.

\section{Discussion}
\label{sec:discussion}

\paragraph{Define reusable features by destination behavior.}
The paired ablation shows that repository evidence helps, and the
source-exposure analysis shows that reading the relevant source does not
guarantee success. An entrypoint tells an agent or tool where to start reading,
but only the destination contract tells it what the new package must do.
Extraction and migration tools should therefore take a behavioral contract as
input and judge a reconstructed capability against it, while leaving the
implementation strategy open.

\paragraph{Verify supporting relationships under changed assumptions.}
In the reviewed failures, the artifact contained source-backed components that
no longer agreed with each other or with the destination. Agents and tools
should therefore check such relationships across the new package boundary, for
example by testing the producer and consumer of a shared representation
together, and should check whether a declared adaptation requires changes below
the exported interface. Inherited behavior and destination-specific requirements
call for different evidence: upstream code and tests support the former,
whereas the latter must be derived from the contract.

\paragraph{Separate behavioral success from implementation and execution characteristics.}
Successful artifacts differ substantially in size and source overlap, and
agents often keep working after a passing artifact exists. These properties
describe how a lift is produced, not whether it is correct. Benchmarks for
software reuse should therefore use behavioral verification as the success
criterion and report implementation footprint and execution effort separately,
as \flb does.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Single runs and descriptive comparisons.}
Each configuration contributes one run per task. Pass rates therefore
describe the observed performance of the evaluated model--harness
configurations rather than run-to-run success probabilities, and bootstrap
intervals reflect variation across tasks rather than repeated runs. Comparisons
across lift types, entanglement mechanisms, and configurations are descriptive:
task categories co-vary with other task properties, and the footprint analysis
is conditional on success, so it neither estimates causal configuration effects
nor extrapolates to tasks on which a configuration fails.

\paragraph{Scope of the measures.}
Passing the evaluator shows that an artifact satisfies the protected tests, not
that it is fully equivalent to the upstream implementation or, for containment
requirements, secure in general. Source exposure indicates that an agent saw
entrypoint-associated source content, not that it understood it. RRES is
relative to one reference package and does not measure minimality, and Copy
measures only syntactic overlap; neither establishes maintainability, semantic
quality, or a deliberate reuse strategy. Finally, the agent could not observe
the first passing checkpoint, so post-checkpoint tokens do not quantify
avoidable cost.

\paragraph{Benchmark scale.}
The current version of \flb contains 150 tasks from 126 repositories, which
provides diverse coverage but cannot exhaust the space of real-world feature-lifting
scenarios. Future versions will expand the benchmark with more tasks, repositories,
and feature types to improve coverage and support broader evaluation.

\paragraph{Language coverage.}
The current benchmark focuses on Python. Feature lifting may exhibit different
characteristics in languages with different type systems, build systems, and
dependency mechanisms. We plan to extend \flb to additional ecosystems,
including Java and Go, to study how well the findings generalize across
programming languages.

\section{Related Work}
\label{sec:related-work}

\subsection{Repository-Level Coding and Feature Development}

SWE-bench evaluates repository patches that resolve real GitHub
issues~\cite{jimenez2024swebench}, and SWE-Bench Pro extends this direction to
longer-horizon software engineering tasks~\cite{deng2025swebenchpro}.
Feature-development benchmarks broaden the objective beyond issue resolution.
FeatBench evaluates implementation from natural-language requirements without
code hints, including whether changes preserve existing
features~\cite{chen2026featbench}. FeatureBench derives tasks through test-driven
dependency tracing and evaluates both incremental development in an incomplete
repository and construction of the requested functionality from
scratch~\cite{zhou2026featurebench}.

Recent benchmarks extend evaluation toward standalone repository construction.
NL2Repo-Bench asks agents to construct an installable Python library from a
natural-language requirements document and an empty
workspace~\cite{ding2026nl2repo}. RepoZero formulates repository generation as
black-box reproduction from API specifications without access to the original
library implementation~\cite{zhang2026repozero}. These settings study construction
from specifications when the source implementation is unavailable.

Unlike these settings, \flb gives the agent the intact source implementation as
evidence and evaluates the result as an independent package without access to
that implementation (Table~\ref{tab:setting-comparison}).

\subsection{Feature Location, Extraction, and Software Reuse}

Program slicing uses dependence analysis to retain statements relevant to a
specified criterion~\cite{weiser1984slicing}, while feature location identifies
source entities associated with a requested concern~\cite{dit2013featurelocation}.
Research on multi-dimensional separation of concerns addresses functionality
that cuts across module boundaries~\cite{tarr1999degrees}. These foundations
explain why recovering a reusable capability can require reasoning beyond its
entrypoint: the implementing statements and their supporting dependencies need
not form an existing module.

Software transplantation turns this recovery problem into executable reuse.
Barr et~al. combine analysis, testing, and search to extract donor functionality
and adapt it to a supplied host~\cite{barr2015transplantation}. Foundry extends
transplantation to software product lines; its prodScalpel tool uses tests and
annotations identifying features and implantation points to extract and
integrate functionality across codebases~\cite{souza2025foundry}.
\flb complements these techniques by evaluating end-to-end reconstruction into
an independent package, leaving localization and implementation strategy to a
general-purpose coding agent.

\subsection{Behavior-Preserving Refactoring and Transformation}

Classic refactoring work defines restructuring operations with preconditions
under which program behavior is preserved~\cite{opdyke1992refactoring}.
EM-Assist combines LLM suggestions with static analysis to
select Extract Method candidates and uses IDE machinery to perform the
transformation~\cite{pomian2024emassist}. SWE-Refactor evaluates atomic and
compound refactorings mined from real Java projects. Its verification combines
project compilation and tests with checks that the requested structural
transformation occurred~\cite{xu2026swerefactor}.

More recently, SWE Refactor Bench studies whole-repository stack migrations and
separates migration completeness from behavioral correctness: its evaluation
verifies that the requested migration occurred in addition to testing preserved
behavior~\cite{hong2026swerefactorbench}.

Feature lifting, in contrast, prescribes destination behavior through a contract
but no structural transformation. Accordingly, artifact size and source overlap
characterize successful implementations but do not determine acceptance.

\subsection{Repository Context and Evidence Utilization}

RepoCoder uses iterative retrieval and generation for repository-level code
completion~\cite{zhang2023repocoder}. RepoBench evaluates retrieval, completion,
and their combined pipeline~\cite{liu2024repobench}, while CrossCodeEval targets
completion requiring cross-file context~\cite{ding2023crosscodeeval}. These works
establish repository information as a resource for generation.
BeyondSWE extends evaluation to tasks requiring evidence beyond the target
repository. Its SearchSWE experiments report limited and uneven gains from search
augmentation and illustrate failures to integrate retrieved information with
local implementation and version constraints~\cite{chen2026beyondswe}.
\flb examines this evidence-utilization problem across a new package boundary
through paired repository-evidence ablation and inspection of
source-exposed failures.

\section{Conclusion}

We introduced \flb, a benchmark for behavior-preserving feature lifting from
real repositories. In feature lifting, agents rebuild an existing capability as
an independent package that preserves the specified behavior without runtime
access to the original repository. Unlike source-code copying, this requires
reconstructing the supporting relationships and adaptations that the
destination needs. \flb makes this setting executable through behavioral
contracts, protected tests, and source-free evaluation.
Our empirical study shows that repository evidence raises pass rates by
32.0--56.0 percentage points, but source access alone does not guarantee a
successful lift: 79.5\% of behavioral failures occur after the agent has read
the relevant source, and recurring failures arise when supporting assumptions,
representations, or destination-specific adaptations are not reconstructed.
Feature lifting thus provides a setting for studying how coding agents reuse
software across package boundaries.
