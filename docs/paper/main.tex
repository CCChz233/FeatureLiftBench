\title[FeatureLiftBench: Behavior-Preserving Feature Lifting]{FeatureLiftBench: Benchmarking Behavior-Preserving Feature Lifting from Real Repositories}
\author{Anonymous Author(s)}

\begin{abstract}
Software reuse often requires moving an existing capability out of its host
project while preserving the behavior that makes it useful. The implementation
may be available, yet its helpers, state, exceptions, and resources must still
be recovered behind a new package boundary. We introduce \flb, a benchmark for
\emph{behavior-preserving feature lifting}. Given a complete pinned repository
and a public behavioral contract, an agent constructs a standalone package
that is tested without access to the source project. The release contains
200 Python tasks from 176 repositories and combines source-free functional
evaluation with separate measurements of artifact size and direct source copying.
We study six OpenHands model--harness configurations on 150 common tasks, with
source-location hints and benchmark tests withheld. Functional pass rates range
from 24.0\% to 76.7\%; strong configurations frequently deliver packages that
fail behavioral checks. The hard3 construction group has lower observed success
after controlling for backend and lift type. Successful extractions also differ:
on 97 tasks passed by both DeepSeek V4 Pro and GPT-5.6 Luna, median size relative
to the task reference is 0.993 and 0.697, respectively. We report configuration
limitations and sensitivity to provisionally flagged task defects, and keep
AI-assisted failure interpretation exploratory. These results motivate evaluating
behavior preservation and extraction footprint separately when assessing agents
for repository-level software reuse.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

A developer may need a parser from a larger tool, a configuration resolver from
a framework, or a signal registry for a new library. In each case, an existing
repository supplies a working implementation, but the desired deliverable is a
component that can run in a different package. Reuse therefore involves deciding
which behavior to preserve and which supporting code must accompany it.
The surrounding application may supply shared state, exception definitions,
resource loading, or initialization that an extracted entry point silently relies on.

Consider a signal registry whose main operation dispatches events to callbacks.
Copying the dispatch loop may appear sufficient until a receiver is garbage
collected, a sender-specific subscription is used, or a client expects repeated
namespace lookups to return the same signal. Those obligations concern the
feature's observable behavior, even when their implementations lie outside its
most obvious method. Retaining more of the host project may preserve that
behavior, but also enlarge the delivered artifact. This creates two questions
for agent evaluation: can the extracted component satisfy its contract on its
own, and what implementation footprint does a successful extraction retain?

Repository agents can inspect code and documentation, trace dependencies, edit
multiple files, and run local checks. Existing evaluations establish important
parts of this capability. SWE-bench and SWE-Bench Pro assess changes that resolve
issues within a project~\cite{jimenez2024swebench,deng2025swebenchpro}; feature
development benchmarks assess implementing requested
functionality~\cite{chen2026featbench,zhou2026featurebench}. FeatureBench includes
construction from scratch as well as incremental development. These settings
leave a distinct measurement question: when the requested implementation is
already available as evidence, can an agent deliver its declared behavior
across a new package boundary? Software transplantation has long studied
donor-to-host reuse~\cite{barr2015transplantation}; we build on that objective
with a benchmark for general-purpose coding agents.

We call the task \emph{behavior-preserving feature lifting}. The agent receives
an intact, pinned source repository and a public contract specifying the output
API and required behavior. It delivers a new \texttt{featurelifted} package,
which is evaluated without runtime access to the donor repository. The source
is deliberately available: the challenge is recovering and packaging a bounded
capability using that evidence. The output contract defines what must remain
observable, while the source-free execution boundary tests whether the artifact
can provide it independently. Agents may extract, adapt, or reimplement code;
the benchmark accepts different implementations that satisfy the requirements.

\flb makes this task measurable through three design choices. First, explicit
API and behavior clauses bound the requested capability within a real source
project. Second, the Full-Repository / No-Hint \mainprotocol protocol provides
the upstream code, tests, and documentation while withholding benchmark tests,
reference solutions, and source-location hints. Third, evaluation separates
functional success from extraction footprint: all four functional gates must
pass, after which artifact size relative to a feasible reference and detected
source copying describe the delivered implementation. This separation permits
comparison of successful reuse strategies without awarding small but incomplete
submissions a better functional score.

The frozen release contains 200 Python tasks from 176 canonical repositories.
Our main study analyzes six OpenHands configurations on the common 150-task
subset; results on the separate 50-task extension appear in the appendix.
Within the main subset, Core-100 and hard3-50 denote construction groups used
to examine variation in observed difficulty. Four research questions organize
the study:
\begin{itemize}
 \item \textbf{RQ1---Capability:} How often do the evaluated configurations
 deliver functionally passing artifacts?
 \item \textbf{RQ2---Failure stages:} Where do attempts fail, distinguishing
 non-delivery from evaluation of a submitted artifact?
 \item \textbf{RQ3---Difficulty:} How does success vary across tasks and
 construction groups?
 \item \textbf{RQ4---Extraction footprint:} On tasks passed by both compared
 configurations, how do artifact size and direct source copying differ?
\end{itemize}

The results show incomplete behavioral preservation alongside variation in
successful extraction. Pass rates range from 24.0\% to 76.7\%, and strong
configurations frequently fail behavioral evaluation after delivering a package.
The hard3 group remains associated with lower success after accounting for
backend and lift type. On 97 tasks passed by both Pro and Luna, median
reference-relative size is 0.993 and 0.697, respectively: the same passing
requirements can be met by artifacts with different footprints. We interpret
these results as properties of the recorded model--harness configurations.
Failure cases provide exploratory explanations, and sensitivity analyses
disclose the effect of provisionally flagged contract/evaluator defects.

The paper makes three contributions:
\begin{itemize}
 \item \textbf{A benchmark for source-backed feature reuse.} We formulate
 behavior-preserving feature lifting and assemble 200 Python tasks with pinned
 repositories, bounded output contracts, and executable reference evidence
 (Section~\ref{sec:benchmark}).
 \item \textbf{An evaluation protocol for independent artifacts.} We define
 the agent's information boundary, functional evaluation without the donor
 repository, and separate size/copying measurements on passing artifacts
 (Section~\ref{sec:protocol}).
 \item \textbf{An empirical study of capability and extraction outcomes.}
 We characterize six configurations on 150 common tasks through success rates,
 failure stages, difficulty associations, and paired artifact comparisons,
 supplemented by defect sensitivity and exploratory failure cases
 (Sections~\ref{sec:results} and~\ref{sec:diagnostics}).
\end{itemize}

Together, the task and study connect repository understanding to a concrete
reuse outcome: a bounded capability delivered as an independently executable
artifact whose behavior and implementation footprint can both be examined.


\section{The FeatureLiftBench Benchmark}
\label{sec:benchmark}

The benchmark connects a reuse request to an observable deliverable. We first
define the contract and package boundary, then describe how source evidence,
task specifications, and executable checks are assembled. Validation records
and dataset composition establish the scope of the resulting collection.

\subsection{Task Formulation and a Running Example}

A task consists of a pinned repository $R$, a public contract $S$, an initial
workspace $W$, and a protected evaluator $J$. A model backend $M$ acting through
an agent harness $H$ produces a submission $A$:
\begin{equation}
 A = \operatorname{Run}(M,H,R,S,W).
\end{equation}
The public contract lists the required API surface, behavior clauses, constraints,
and exclusions. Source identity records establish which upstream snapshot defines
the behavior being lifted. The agent can inspect that snapshot but must place the
result inside the designated submission directory.

The contract determines the scope of preservation. A task may require a selected
configuration operation or registry behavior without requiring the entire
upstream project. APIs, return values, exceptions, mutation, ordering, or resources
are obligations when specified by the task. Direct extraction, adapted code, and
reimplementation are legal strategies. This permits multiple passing artifacts
and avoids grading against a single required source slice.

The functional score is
\begin{equation}
 F(A)=B(A)\land T_{\mathrm{public}}(A)\land T_{\mathrm{hidden}}(A)\land I(A),
 \label{eq:functional}
\end{equation}
where $B$ is the evaluator's package loading/build gate, $T$ denotes the two
behavioral test groups, and $I$ denotes its explicit isolation checks. The tests
execute in an environment without the source repository. Consequently, a
dependency on a missing source path can fail during loading or behavioral tests,
before the separate Isolation gate becomes the first failing gate. Gate names
must not be interpreted as independent semantic failure causes.

\paragraph{Running example: a signal registry.}
The Blinker task asks for \texttt{Signal}, \texttt{Namespace}, and \texttt{ANY}
under the new \texttt{featurelifted} namespace. The public contract requires
sender-specific dispatch, receiver responses, cleanup of weak receivers after
garbage collection, stable signal identity within a namespace, and scoped
connection/disconnection. It excludes asynchronous receivers and the upstream
global named-signal singleton. A plausible dispatcher can therefore remain
incomplete even if its main \texttt{connect} and \texttt{send} methods work:
receiver lifetime and namespace identity are also part of the requested behavior.
The final artifact may retain upstream code or reimplement these obligations,
but may not import \texttt{blinker} or read the donor tree at runtime.
Figure~\ref{fig:pipeline} summarizes this source-to-artifact boundary using only
the public task contract.

\subsection{Task Construction and Source Provenance}
\label{sec:construction}

Construction links an upstream capability to a bounded public specification,
protected behavioral checks, and an executable reference artifact. The steps
below describe the release's construction rules and supporting implementation.
The collection accumulated across several construction rounds; the available
records do not establish that every early task was produced by one automated
pipeline or drawn from a common enumerated candidate pool.

\paragraph{Selecting a capability and pinning its source.}
Candidate capabilities come from Python libraries, developer tools, and framework
components. Selection guidance favors reusable behavior with inspectable source
and supporting tests or documentation, a scope that can be stated explicitly,
and an offline evaluation environment. Examples include parsing, configuration
resolution, registries, and resource handling. Tasks requiring live services or
uncontrolled external state conflict with this evaluation boundary. This is a
curated collection: it does not estimate how frequently developers request each
kind of extraction. The extension has a recorded selection ledger containing
50 selected candidates and 20 backups; these counts describe that construction
round, not the candidate universe for the complete benchmark.

Each selected capability is associated with a canonical repository identity and
an immutable commit. The full-repository source policy retains the tracked tree,
including upstream tests, documentation, examples, configuration, and resources,
with uniform exclusions for repository administration and untracked artifacts.
It does not prune files according to the target feature. The source registry
records both an archive digest and a source-tree digest, separating the identity
of the transported archive from that of its contents. A repository can contribute
more than one snapshot. Providing the intact donor preserves the need to locate
and understand relevant code before establishing a new package boundary.

\paragraph{Specifying the observable contract.}
Task authors identify the capability's entry points and define what a client of
the extracted package must observe. Structured public specifications enumerate
required APIs, signatures, defaults, members, and exceptions, together with
behavior clauses carrying stable identifiers. Clauses describe relevant inputs
or preconditions, operations, and observable outcomes; exclusions delimit the
parts of the donor that the task does not request. Dependency declarations and
forbidden upstream imports specify the permitted runtime boundary. For example,
the signal-registry contract retains receiver lifetime and namespace identity
while excluding asynchronous dispatch. Thus, bounded scope still requires
preserving the interactions explicitly included in the contract.

The human-readable task statement is rendered from this structured specification.
The Main agent view omits source-location hints and evaluator-only metadata;
provenance entry points can remain in internal task records without being
included in the prompt. This separates the requested behavior from a prescribed
implementation location. The renderer and specification hashes make changes to
the agent-visible request traceable.

\paragraph{Building checks and a reference artifact.}
Each task package pairs its contract with two behavioral test groups and a
reference implementation. The construction rules assign basic checks to Public
and deeper cases to Hidden, while requiring both groups to remain within the
declared contract. Evaluator-side mappings link tests to behavior identifiers
and required APIs. Required obligations must have mapped coverage; optional or
excluded behavior must not become an undeclared requirement. Mapping coverage
is mechanically inspectable, whereas whether an assertion follows from a clause
still requires semantic judgment. Both test groups and the reference are withheld
from the agent in Main; ``Public'' is a test-group name, not a statement that
its contents are visible in this condition.

The reference provides a concrete, source-independent implementation of the
requested contract. It is checked through the evaluator and subsequently fixed
as a measurement reference. The release records 150 Python-150 oracle artifacts
and 50 extension reference solutions. These artifacts demonstrate one feasible
implementation per task; they do not define a unique correct implementation,
prove minimum code size, or restrict the agent's extraction strategy.

\paragraph{Versioning the assembled release.}
A candidate freeze binds task and specification hashes, generated statements,
source identities, references, evaluator code, and policy files. The final freeze
additionally checks the pinned execution environment and reference replay record.
This separates content assembly from executable validation and lets a later
repair be identified as a version change. Scripts perform rendering, structural
checks, digest computation, and freeze assembly. Recorded LLM review and
maintainer-proxy adjudication apply to a documented repair scope, detailed next;
they do not establish uniform human authorship or independent human review of
all tasks.

\subsection{Validation Evidence and Quality Boundaries}
\label{sec:validation}

Validation addresses three complementary questions: whether the task refers to
the intended source, whether its assets agree on the requested contract, and
whether an independent artifact can satisfy the evaluator. Table~\ref{tab:dataset}
summarizes the recorded coverage; Figure~\ref{fig:construction} places these checks
at the boundary between construction and release.

\paragraph{Source and package consistency.}
The candidate record reports verified archives for all 182 source snapshots and
source mappings for all 200 tasks. Package validation checks required assets,
metadata shape, task identity, and consistency between allowed dependencies and
the lock file. Contract validation checks generated statements and specification
hashes, required API and behavior coverage, and the existence of mapped test
identifiers. The freeze records 200 successful task checks. These checks support
traceability and structural consistency: for example, a stale generated statement
or a mapping to a nonexistent test is an actionable construction error. The
archive counts report the saved candidate validation, not a new download or
reverification performed during paper preparation.

\paragraph{Reference feasibility and repeatability.}
The final release records three passing oracle executions for each of the
200 tasks, yielding 600/600 passing runs and 200/200 stable fingerprints. The
replay checks the functional gates and recorded sandbox/provenance outcomes in
the designated evaluation environment. A stable fingerprint means these recorded
outcomes agree across the three repetitions; it does not require byte-identical
logs. This establishes that each recorded reference can satisfy its evaluator
repeatedly. It does not establish semantic completeness, adversarial robustness,
or equivalence between the oracle environment and every retained agent run;
the latter provenance boundary is discussed in Section~\ref{sec:protocol}.

\paragraph{Contract review and its limits.}
The freeze v2 repair ledger covers 38 distinct tasks, addressing undeclared API
members, incorrect source entrypoint metadata, and identical Public/Hidden test
bodies. The closed review records LLM review of all 38 repaired tasks and a
separate coding-agent maintainer-proxy adjudication of six scope judgments.
These records explicitly mark independent human review and gold status as false.
They document a bounded repair process, rather than an independent semantic
audit of the complete collection.

A protected expectation should be licensed by the public contract and supported
by upstream behavior. API, mapping, hash, overlap, and execution checks test parts
of this relation but cannot establish semantic entailment. Later failure
inspection flagged seven potential contract/evaluator defects, which we disclose
and use in a post hoc sensitivity analysis (Section~\ref{sec:defects}). We retain
the frozen tests and recorded outcomes in the main results. Reference success
and zero unresolved items in a particular repair ledger therefore should not be
read as a claim that every evaluator expectation has been independently verified.

\subsection{Dataset Composition}
\label{sec:suite}

Figure~\ref{fig:construction} distinguishes construction from completed validation.
The 200-task release consists of Python-150 and an additional 50-task extension
called Hard-50 in the artifact. The main six-backend comparison uses Python-150:
all six have results on these task IDs, and all passing submissions have the
reference-relative measurements used in this paper. Five backends also have
200-task results; Pro was evaluated on the 150-task subset. The 200-task
functional table is provided in Appendix~\ref{app:extension}, rather than
combining unequal model coverage into the main table.

Within Python-150, Core-100 and hard3-50 are construction groups. The
\emph{hard3-50 group belongs to Python-150}; it is not the additional Hard-50
extension. We retain these historical group names for reproducibility and test
their empirical relationship to performance without treating them as universal
categories of software difficulty.

\paragraph{Source and functional coverage.}
Canonical repository IDs in the freeze identify 126 repositories and 132
snapshots in Python-150, plus 50 repositories and 50 snapshots in the extension.
The repository sets are disjoint, yielding 176 repositories and 182 snapshots
in the complete release. Repository aliases are normalized before counting.
These units distinguish the number of extraction tasks from both project
diversity and the number of pinned source versions.

The existing task-family inventory spans ten groups. Joined to the release by
task ID, its largest groups are registry/plugin dispatch (38 tasks),
parsing/tokenizing/decoding (37), configuration resolution/discovery (26),
validation/normalization/construction (22), and serialization/formatting/rendering
(19). The remaining 58 tasks cover workflow/session orchestration, resource and
metadata loading, algorithms and data structures, protocol state transitions,
and cache/retry policies. These are historical descriptive annotations, not
fresh semantic labels for every frozen snapshot: 44 inventory rows record a
different source commit from the current freeze. We use the families to describe
the collection's breadth, not as audited categories for performance claims.

\paragraph{Lift types and representative tasks.}
The lift taxonomy distinguishes preserving a principal upstream capability
(\emph{Direct}), adapting its interface or behavioral boundary (\emph{Adapted}),
and combining capabilities without a single corresponding upstream API
(\emph{Composite}). The labels characterize the requested transformation;
they do not prescribe how an agent must implement its answer.
Table~\ref{tab:dataset} gives the completed Python-150 label distribution.

The Direct-labeled Blinker task illustrates preservation of a coherent signal
registry, including interactions beyond its most visible dispatch operation.
The Adapted-labeled \texttt{build} task exposes source-directory validation and
build-system-table parsing under the new package API, while excluding network
access, isolated-environment creation, and actual wheel builds. Its requested
boundary selects validation behavior from a larger build workflow. As a
Composite example, the extension's \texttt{zope.interface} design combines
interface declarations, inheritance, named adapter registration, and single-
and multiple-object adapter queries. That example carries a planned ledger
label: the extension's 50 lift labels remain construction annotations, whereas
the 150 main labels have completed annotation status. Neither status establishes
independent human validation.

Feature-family, lift-type, and entanglement annotations are withheld from the
agent and do not affect scoring. All headline tasks share the high
entanglement-level label, so that label cannot support an empirical difficulty
contrast here. Appendix~\ref{app:provenance} indexes all 200 tasks, separating
current frozen source identities from inherited annotations.

\section{Evaluation Protocol and Experimental Setup}
\label{sec:protocol}

The evaluation instantiates the task boundary in a concrete agent workflow.
We specify the available information and recorded configurations, define
functional and footprint measurements, and describe how saved runs enter the
comparison. These choices determine what a reported score measures.

\subsection{Information Boundary and Agent Configurations}

We evaluate DeepSeek V4 Pro, DeepSeek V4 Flash, GPT-5.6 Luna served through
OpenLux, GLM-5.3-Flash, Qwen3.6-35B-A3B-FP8, and GPT-OSS 120B. Below, we
abbreviate them as Pro, Flash, Luna, GLM, Qwen, and OSS. The agent image records
OpenHands CLI 1.16.0. The common protocol supplies the complete pinned repository,
withholds benchmark tests and source-location hints, and uses the standard task
prompt. Agents can inspect upstream tests and create their own probes. Public
feedback and source-hint ablations are not pooled into this study.

The configured envelope is 120 steps, 131,072 context tokens with 8,192 reserved,
and a 3,600-second task timeout. Main does not impose the separate two-million
token cap used by the historical cost arm. Runtime statistics such as recorded
assistant messages are not necessarily identical to the configured action budget.
The evaluated object is a backend embedded in its recorded OpenHands/provider
profile, not a base model independent of tool calling, serving, and recovery.

Context handling is not identical across backends. Pro and Flash use the
token condenser with a 122,880-token trigger and a 61,440-token target; Luna,
GLM, Qwen, and OSS record the default condenser without explicit token thresholds.
Table~\ref{tab:config} reports these settings and the result provenance.

\subsection{Functional Evaluation and Extraction Metrics}

Only the collected submission enters the evaluator capsule. The original
repository is absent from the runtime import path, evaluation uses the frozen
dependency environment, and the container disables networking. The frozen image
records Linux/amd64 and Python 3.11.14, with a read-only root filesystem and
dropped capabilities. Agent and evaluator image identities are recorded in the
freeze manifest.

\textbf{Build} resolves and loads the submitted package according to the
evaluator's installation/path-loading policy. In this release, a direct package
directory can be loaded through \texttt{PYTHONPATH}; an editable-install failure
can also use a path fallback. Thus a Build pass demonstrates usability under the
frozen evaluator policy, not that a wheel or clean package-manager installation
has been independently validated. \textbf{Public} tests exercise primary
contract behavior, and \textbf{Hidden} tests cover additional cases and
combinations intended to follow the same public contract. \textbf{Isolation}
checks include forbidden source imports and protected-path restrictions.
All four outcomes are required by Equation~\ref{eq:functional}.

We report two complementary views. An exclusive first-outcome classification
uses Missing, Build, Public, Hidden, then Isolation, with Pass for a fully
successful artifact. A non-exclusive view counts failed gate flags among
delivered artifacts; these counts can overlap. A failed flag can reflect a
preceding loading failure and is not necessarily evidence that all tests in that
group executed. \emph{Isolation residual} denotes artifacts that pass Build,
Public, and Hidden but fail Isolation. This is a measured residual category,
not the prevalence of all source-dependency mistakes.

\paragraph{Extraction measurements.}
\label{sec:metrics}

For a passing artifact $A$ and a frozen feasible reference $A_{\mathrm{ref}}$,
Reference-Relative Extraction Size is
\begin{equation}
 \operatorname{RRES}(A)=
 \frac{\operatorname{PythonLOC}(A)}{\operatorname{PythonLOC}(A_{\mathrm{ref}})}.
 \label{eq:rres}
\end{equation}
The evaluator uses its Python source-line counting convention consistently for
both artifacts. An RRES of one means equal counted size, not equal code or
optimality. The reference demonstrates one feasible implementation; it is not a
proof of a minimum semantic closure.

The copied-code diagnostic estimates the fraction of submitted lines matched
to source code in runs of at least three normalized non-empty, non-comment
Python lines. It can miss rewritten equivalents and count shared idioms. It is
neither a licensing judgment nor a direct measure of maintainability. These
metrics are computed in a trusted read-only stage after functional evaluation;
the metrics stage does not execute the submitted code.

Footprint summaries are conditioned on functional success. Because different
backends pass different tasks, unpaired medians are descriptive only. Comparisons
between backends use their same-task common passing set. Low RRES or low detected
copying cannot compensate for a functional failure, and neither is folded into
the primary pass score.

\subsection{Result Assembly and Statistical Protocol}

The analysis retains one collected outcome per model--task cell, yielding
900 cells over 150 common task IDs. Empty submissions remain failures, including
tool-validation and early-exit events. Run status is separate from evaluator
correctness. The campaign includes preflight replacements and runner-level
transient recovery, whose records are retained. We report the final collected
functional outcome under that policy; this is not a repeated-run estimate or a
claim that every task used exactly one uninterrupted process invocation.

\paragraph{Task inputs and retained run identities.}
The release specification has freeze identity \texttt{6c20ff03\ldots}; the
result matrix retains 522 rows with that identity and 378 with predecessor
identity \texttt{0b106842\ldots}. The manifests agree on the specification and
full task-tree records of 126 tasks; 24 tasks changed. Flash, Luna, and Qwen
each replace exactly those 24 tasks and retain 126 unchanged-task runs. Pro,
GLM, and OSS each contribute 150 v2 rows (Table~\ref{tab:config}).
An offline audit checks content as well as these labels: all 900 captured initial
task prompts match the v2 rendering, all 900 dependency locks agree, and the
recorded task-specific specification and source identities match v2. All 838
available evaluator results carry functional-capsule digests matching the
reconstructed task inputs; the other 62 cells remain failures. Thus the main
comparison uses aligned task inputs while preserving historical run identities.

All 900 run records also report the same agent/evaluator image-ID pair. These
IDs differ from the release/oracle manifest's image-ID fields, and the saved
evidence does not explain that difference. We therefore do not claim byte-identical
oracle and campaign environments. Backend-specific context handling, provider
behavior, and recovery policy also remain part of each measured configuration.
Statistical comparisons describe those configurations and do not isolate the
effect of changing only the model. Appendix~\ref{app:reproduction} gives audit
details and the remaining local-file discrepancies.


We report Wilson 95\% intervals for functional pass proportions and selected
two-sided exact McNemar tests for paired model outcomes. Reported $p$-values are
unadjusted exploratory comparisons; they do not establish a total ordering of
backends. To study difficulty, we fit pass/fail against backend, construction
group, and lift type, with standard errors clustered by task. The model estimates
associations within this curated collection, not causal effects of construction.
For paired copying we report Wilcoxon signed-rank tests and matched-pairs
rank-biserial effect sizes.

One retained observation per cell does not estimate stochastic run-to-run
variance. Multiple tasks from a repository can also share behavior and failures;
task-level intervals and standard errors do not model every repository-level
dependence. The scores below retain the frozen task set. The separately labeled
known-defect sensitivity view is post hoc and uses only existing outcomes.

variation across tasks. Finally, comparisons on common successes reveal
implementation differences that a pass/fail score alone does not describe.

\section{Diagnostic Analysis and Discussion}
\label{sec:diagnostics}

The quantitative results establish what happened under the recorded protocol.
This section examines how contract/evaluator disagreements affect their
interpretation, uses artifact cases to explore incomplete behavior recovery,
and derives implications for future agents and benchmark design.

\subsection{Contract Defects and Sensitivity}
\label{sec:defects}

Failure inspection flagged seven tasks for potential disagreement between the
public contract and evaluator expectations. A subsequent offline close-read of

supports retaining six candidates involving undeclared interfaces, unspecified
normalization, output markers, or conflicting default-version rules. The seventh,
concerning marker-description whitespace, remains an accessor-policy ambiguity:
preserving whitespace in a split function need not require preserving it in a
registry accessor. All seven retain the provisional label

\subsection{Exploratory Evidence on Behavioral-Contract Recovery}

The existing close-read examines the public contract, first-failure evidence,
and submitted code for every Pro/Flash artifact failure, with trajectory
inspection to check source access. After the defect-row exclusion, the common
symptoms are behavioral drift and incomplete API obligations. We use
\emph{contract-closure gap} as a descriptive term for a delivered artifact
that omits or changes required observable behavior despite implementing a
substantial part of the target. A Hidden failure alone is insufficient for this
label: the failed expectation must first be supported by the public contract.

For example, in an Alembic revision-map task, both backends expose the requested
lookup API but resolve a literal revision identifier as a symbolic base marker.
The failure concerns precedence between two interpretations, rather than an
absent top-level function. An aiohttp task similarly contains validation logic
while leaving a required exceptional path incomplete. These examples illustrate
how apparent implementation coverage can coexist with a missing behavioral
obligation; they do not disclose protected test assertions.

Every retained Pro/Flash failure has recorded repository inspection. This rules
out a narrow explanation that the agent never inspected source files. It does
not establish that all relevant implementation regions were located or understood.
The coding therefore concerns observable artifact symptoms, not a causal
decomposition of search, reasoning, and editing. The analysis remains an
assistant first pass, without independent human agreement measurements.
Appendix~\ref{app:diagnostic-counts} provides provisional counts and a separate
stratified sample from Luna, Qwen, and OSS; neither is presented as a validated
cross-model root-cause distribution.

\subsection{Implications for Feature-Lifting Agents}
\label{sec:discussion}

\paragraph{A boundary-sensitive evaluation of software reuse.}
The benchmark makes the output boundary part of correctness. The upstream
project provides implementation evidence, but the submitted artifact must work
without that project. This links the long-standing reuse and transplantation
problem to the capabilities of interactive coding agents. The contribution is
the task collection and measurement protocol, rather than a claim that software
extraction is a newly discovered activity.

\paragraph{From visible APIs to complete behavior.}
Strong backends frequently produce loadable packages while missing required
behavior. The exploratory cases suggest that tracking API presence alone can
overstate implementation completeness: a branch, default, state transition, or
exception can remain incorrect behind an otherwise plausible interface. A useful
direction is to connect each public obligation to repository evidence and
implementation evidence. The present study motivates that direction but does
not demonstrate that an obligation ledger, additional reflection, or a repair
loop improves the benchmark score.

\paragraph{Preserve multiple dimensions of extraction quality.}
A correct artifact can be large relative to its reference, while a small
artifact can fail required behavior. Common-success comparisons isolate
footprint differences from differing task success sets, but still do not
measure downstream maintenance effort. Reporting correctness, relative size,
and detected copying separately avoids rewarding an incomplete implementation
for being small or penalizing faithful reuse solely for retaining source lines.

\paragraph{Benchmark validation is an ongoing evidence problem.}
Stable reference execution and mechanically consistent metadata are necessary
checks, but do not establish that every evaluator expectation follows the task
statement. The later defect flags make that limitation concrete. Freezing the
recorded results, disclosing suspect tasks, and labeling exclusion sensitivity
allows readers to assess their influence without changing the benchmark
retrospectively. Future releases can repair adjudicated defects under a new
identity; the current results retain their recorded run identities.

\section{Threats to Validity}
\label{sec:threats}

\paragraph{Construct validity.}
Finite behavioral tests cannot prove equivalence to every behavior of an upstream
feature. The output contract deliberately covers a bounded capability, and
passing should be interpreted within that scope. Contract/evaluator disagreements
can misclassify agents; the seven flagged tasks and sensitivity analysis expose
known concerns without certifying the remaining tasks. Build allows path loading
and therefore does not prove wheel validity or clean installability. Isolation
is also an operational check: dependency mistakes may surface at other gates,
and the environment's available packages can mask undeclared dependencies.

\paragraph{Internal validity.}
Outcomes depend on source materialization, dependency locks, agent/evaluator
images, prompt and context handling, model endpoints, and recovery logic.
The release records identities for these components. The offline audit aligns
captured prompts, locks, recorded source identities, and available functional
capsules across the two retained run-freeze identities. However, the run image
IDs differ from the release/oracle manifest fields without a documented
explanation. Pro/Flash also use different condenser settings from the other
backends. These factors limit attribution of score differences to model
capability alone. Information ablations are excluded. In addition,
provider behavior and model-specific tool-call compatibility remain part of the
measured system. One final collected outcome per task does not remove effects
of preflight replacement or transient recovery. Reproduction must preserve the
recorded campaign policy as well as the visible task specification.

\paragraph{External and statistical validity.}
The task set emphasizes Python libraries and developer tooling. It does not
establish results for other languages, interactive applications, distributed
services, or industrial migration workloads. Popular source projects may have
appeared in training data; source availability is intentional, while training
contamination is not measured. Construction-group and lift-type associations
are specific to a curated, imbalanced collection. A single outcome per cell
does not estimate sampling variation across repeated runs. Reported task-level
intervals and exploratory tests also do not fully account for shared repository
origins or multiple comparisons.

\paragraph{Annotation and footprint validity.}
Failure and defect labels are AI-assisted and have no independent human L2
validation. Their scope is a strong-backend census and a separate stratified
sample, not a representative six-backend causal taxonomy. Repository access is
not proof of successful localization. RRES depends on the feasible reference
and line-counting convention, and direct-copy detection is a syntactic proxy.
Neither metric establishes minimality, maintainability, or semantic superiority.
The post hoc defect exclusion is derived from observed failures and is not an
exhaustive fairness audit.

\section{Related Work}
\label{sec:related-work}

We position feature lifting along four dimensions: the implementation evidence
available to the agent, the behavior it is asked to deliver, the environment in
which that deliverable is evaluated, and the properties measured after success.
These dimensions connect \flb to software reuse research while distinguishing
its task from issue resolution and feature development.

\subsection{Slicing, Feature Location, and Software Reuse}

Program slicing retains statements relevant to a specified slicing
criterion through dependence analysis~\cite{weiser1984slicing}. Feature location
asks which source entities implement a concern, with techniques drawing on
different forms of static, dynamic, and textual
evidence~\cite{dit2013featurelocation}. Separation-of-concerns research studies
decomposition when concerns overlap across a module
hierarchy~\cite{tarr1999degrees}. These lines of work explain why recovering a
capability may require reasoning across several implementation regions.
They also provide possible techniques for agents solving \flb tasks.
Our evaluation target is the delivered package: locating relevant code is useful
only insofar as the resulting artifact satisfies the declared behavior on its own.

Automated software transplantation is a close antecedent. Barr et~al. use
lightweight annotations, analysis, testing, and search to extract donor
functionality and integrate it into a host~\cite{barr2015transplantation}.
Their formulation already treats preservation during extraction as an
executable objective. \flb evaluates repository agents under a different
interface: the donor and output contract are supplied, source-location hints
are withheld, and the destination is a standalone package rather than a supplied
application integration site. It leaves extraction strategy open, including
behaviorally compatible reimplementation. The benchmark measures satisfaction
of finite obligations and artifact footprint, without asserting semantic
equivalence to the entire donor or minimality of the extracted program.

This relationship also shapes the evaluation criteria. A source slice is not a
required answer, and similarity to one implementation does not define functional
success. Multiple packages can meet the same contract. Reference-relative size
and detected copying characterize those packages after behavioral evaluation;
they do not establish that a smaller package is easier to maintain or that a
rewrite is preferable to faithful reuse.

\subsection{Executable Coding and Feature-Development Benchmarks}

HumanEval evaluates function synthesis from docstrings through execution
tests~\cite{chen2021codex}. SWE-bench instead supplies an issue and a repository
snapshot, then evaluates a proposed patch in the revised
project~\cite{jimenez2024swebench}. Its issues can include feature requests as well
as bug reports. SWE-Bench Pro extends issue-oriented evaluation toward
longer-horizon changes, augments task descriptions with requirements and relevant
interfaces, and examines agent failures~\cite{deng2025swebenchpro}.
These benchmarks motivate executable repository tasks and explicit requirements;
their requested outcome remains a change to the target project.

Feature-development benchmarks are particularly relevant. FeatBench supplies
natural-language requirements and a base-commit repository, withholding code
hints such as file paths and signatures~\cite{chen2026featbench}. FeatureBench
specifies callable interfaces and constructs tasks by removing target
functionality. Its L1 setting retains the incomplete repository, whereas L2
removes the repository during inference and requests construction from
scratch~\cite{zhou2026featurebench}. Accordingly, standalone feature construction
is already covered by prior work. Our question concerns the agent's use of the
intact implementation as evidence for a new artifact, under an execution
boundary that removes the donor from the submitted package's runtime.

Table~\ref{tab:positioning} compares these task interfaces. In \flb, exposing the
complete donor is intentional: it makes source-backed reuse the object of
measurement. The output API fixes the client's expected interface, while
source-location hints remain absent. This is a different information choice
from FeatBench's omission of code-level interface hints. The comparison concerns
what each evaluation asks an agent to do; scores from different task collections
do not establish which setting is intrinsically harder.

construction; it is not a runtime dependency available to the submitted artifact.

\subsection{Agent Runtimes and Evaluation Scope}

SWE-agent studies interfaces through which language models navigate repositories,
edit files, and execute tests~\cite{yang2024sweagent}. OpenHands supplies an
extensible platform for developer agents with sandboxed tool
execution~\cite{wang2025openhands}. Harness-Bench directly examines variation
across model--harness configurations under shared tasks and
budgets~\cite{yao2026harnessbench}. These studies motivate reporting the harness
and its context-handling policy as part of the evaluated system. Our experiments
use OpenHands to instantiate the feature-lifting task; the results characterize
the recorded configurations rather than establishing a harness-independent
ordering of models.

Terminal-Bench evaluates diverse command-line tasks using task-specific
environments and executable verification, with separate discussion of
construction, validation, difficulty, and error
analysis~\cite{merrill2026terminalbench}. OSWorld supports computer tasks with
explicit initial-state setup and execution-based evaluation across desktop
applications~\cite{xie2024osworld}. They provide broader settings for agent
interaction, while \flb focuses on the boundary between a donor repository and
a reusable software artifact. Their treatment of environments and verification
also motivates separating our source provenance, reference execution evidence,
and semantic task-validity discussion. Repeatable execution and fair behavioral
expectations are related requirements that need different supporting evidence.

\section{Conclusion}

\flb turns source-backed feature reuse into an executable task for coding agents:
given an intact repository and a bounded public contract, deliver a package
that preserves the requested behavior without runtime access to the donor.
The benchmark comprises 200 Python tasks and an evaluation protocol that
separates functional success from the footprint of successful artifacts.

Across six OpenHands configurations on 150 common tasks, pass rates range from
24.0\% to 76.7\%. Behavioral checks remain a frequent point of failure for strong
configurations, and the hard3 construction group has lower observed success.
On tasks passed by both compared configurations, artifact size and detected
copying still differ. These findings connect the benchmark's two measurement
goals: establishing that a capability survives a package boundary and describing
the implementation retained to achieve that outcome.

Configuration differences, unresolved environment records, and provisional
defect labels bound the interpretation; our failure cases remain exploratory.
Within that scope, \flb provides a basis for studying how agents recover required
behavior from available source and construct independently executable components
for software reuse.

\section{Flagged Task Identities and Sensitivity}
\label{app:defects}

The existing first-pass defect summary identifies the following task IDs. An
offline L1 recheck inspected both Pro and Flash submissions for each task;
the explanations below distinguish observed implementation differences from
the adapted interfaces required by evaluation.
\begin{itemize}
 \item \texttt{click\_\_lazy\_command\_core\_\_hard3\_001}: evaluation
 requires an undeclared collection invocation interface. Pro omits that member;
 Flash inherits a method with a different invocation convention.
 \item \texttt{flake8\_\_plugin\_options\_core\_\_hard3\_001}: the contract
 requires option registration but leaves the tested member and mapping-style
 access unspecified. Pro uses another registration interface; Flash implements
 the called member but stores options as a list, as does upstream.
 \item \texttt{hatch\_\_project\_metadata\_core\_\_hard3\_001}: evaluation
 selects a space-normalization policy absent from the public contract.
 Upstream contains both strict and non-strict alternatives, so the issue is
 which policy the task requires.
 \item \texttt{pluggy\_\_hook\_wrapper\_core\_\_hard3\_001}: both artifacts
 implement historic calls with the upstream callback-first signature. The
 evaluator uses a different positional convention, causing duplicate assignment
 of the callback argument; this is not an absent-method failure.
 \item \texttt{pytest\_\_ini\_markers\_core\_\_001}: both artifacts preserve
 description whitespace through the registry. The contract explicitly requires
 preservation in the split function but leaves the accessor policy ambiguous.
 This case remains unresolved, rather than a demonstrated direct contradiction.
 \item \texttt{readme\_renderer\_\_content\_type\_core\_\_hard3\_001}:
 rendered HTML is rejected for lacking a literal renderer marker that the
 contract does not require.
 \item \texttt{setuptools\_scm\_\_version\_normalize\_core\_\_hard3\_001}:
 the nonempty default node and the public local-version rule disagree with the
 expected base-only version. Upstream exact-tag formatting explains the latter
 policy but does not remove the contract conflict.
\end{itemize}
The sensitivity script removes these same IDs for every backend and recomputes
counts from the existing 900-row result matrix. It validates key uniqueness,
common task membership, and agreement with the recorded evaluator gates.
Exclusion does not assert that every failure on these tasks has the same cause:
one backend may fail earlier for an unrelated dependency problem. These task
flags are provisional and were discovered through failure analysis, which
limits any claim that the remaining subset is free of defects.

As a further sensitivity check, excluding only the six supported candidates
while retaining the ambiguous pytest task gives a denominator of 144. The
unchanged numerators yield 79.9\%, 75.0\%, 70.8\%, 47.2\%, 43.8\%, and 25.0\%
for Pro, Flash, Luna, GLM, Qwen, and OSS, respectively. Neither this view nor the
143-task view defines a corrected release. The 63-row provisional failure
taxonomy remains conditional on excluding all seven candidates; changing that
choice would require revisiting the two affected failure labels.

\subsection{Delivery and Interaction Records}

Process evidence helps interpret failed delivery. Qwen's 25 empty Python-150
submissions are associated with tool-validation failures involving required
tool-call fields. GLM's 38 empty submissions are predominantly early terminations
without a package; only one is tagged as a tool-validation event. These are
different model--harness outcomes and should not be pooled into behavioral
failure categories. Conversely, 82 Flash passing artifacts have runner status
other than passed, illustrating why workflow status cannot replace evaluation.

Provider token accounting is incomplete and heterogeneous. Luna and GLM lack
verified token totals for this analysis. Pro and Flash expose cache accounting,
allowing an incremental measure of uncached prompt plus completion tokens;
their overall medians are approximately 88.0k and 123.6k. Qwen and OSS have
provider total-token counts without the same cache breakdown. We therefore
do not rank all six backends by token cost.

Within Pro and Flash, hard3 is associated with more interaction and lower
success. Median incremental tokens rise from 81.5k to 118.3k for Pro and from
108.3k to 202.9k for Flash between Core and hard3. This is an observational
association: difficult tasks may induce longer attempts. It does not show
that additional budget is ineffective, or that a different stopping policy
would improve performance.
