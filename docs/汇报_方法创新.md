# 方法创新回顾（简明版）

> 历史 pilot / 负结果 · 不是 Main leaderboard · 2026-08-06

---

## 我们试过什么

除了「先写测试 / 先立合约再实现」这类流程干预，还试过给 Agent 加**额外支架**：

| 方向 | 在做什么 |
| --- | --- |
| **AST / 结构分析支架** | 用上游 AST、依赖与结构信息辅助出题、补 API/方法义务、收紧合约 |
| **上下文压缩 / 导航支架** | 压缩或裁剪仓库上下文、RSG start-here 类「先看哪里」、检索/support 导航 |
| **测试 / 合约脚手架** | 自编探针、原仓执行事实、模板或自出合约、实现后差分修补 |

想法都是：模型自己搞不定闭包时，由工具多喂结构、少喂噪声、或提前钉住行为。

---

## 效果

**这些支架都没有稳定抬高 Functional Pass。**

- AST / 结构义务：能修局部接口，难变成整体过关
- 上下文压缩 / start-here：定位或许更省事，**Hidden / 最终正确率不稳涨**
- 测试/合约先行：最多 Public 好一点，常零翻盘，有时更差、更贵

---

## 为什么不行（汇报主结论）

现在的 coding 模型在 **搜代码、读仓库、局部改写** 上已经很强；FeatureLift 真正难的是 **目标行为/契约对齐**，不是「找不到文件」或「上下文太长」。

再叠 AST、压缩上下文、导航、自建合约等**额外支架**，往往只是：

- 多了一层仪式或局部提示；
- 或把错误故事冻得更死；

**对主瓶颈帮助有限。**
缺的不是更花的脚手架，而是与本题目标语义真正对齐的行为约束——而这恰恰很难靠外挂支架自动给对。

---

## 一句话

> 我们试过 AST、上下文压缩/导航，以及测试–合约类支架；在当前强模型上，再加这些额外支架仍不够管用——能力瓶颈已不在定位与读仓，而在契约级行为闭合。
