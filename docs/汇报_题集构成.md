## 1. Executive Summary

1. **规模：** 200 题，来自 **177** 个固定 commit 的 Python library/tooling 仓库（150 baseline + 50 External；一仓可多题）。  
2. **任务分层：** 三轴 taxonomy——10 类 **feature family**、6 类 **primary entanglement mechanism**、3 类 **lift type**；最大功能族为 parse/tokenize/decode（18%），最大主纠缠为 data-model（30%）。  
3. **难度与批次：** 当前**尚无**统一、经验证的 easy/medium/hard 科学难度标签；batch-1/2/3 与 External-50 属于建设历史，不是 benchmark 的科学属性。

## 3. Task Taxonomy

任务按三轴分层，**不是**按 GitHub topic：

| 轴 | 含义 |
| --- | --- |
| **Feature family** | 目标能力属于哪类行为 |
| **Primary entanglement mechanism** | 为何难从仓库中独立抽离并保持行为 |
| **Lift type** | 交付功能与上游实现如何对应（Direct / Adapted / Composite） |

### 3.1 Feature Family

目标功能的行为类别（如 parse、serialize、config resolve）。共 **10** 类；分布见 §5。

### 3.2 Primary Entanglement Mechanism

目标功能难以干净分离的**主要**原因（dominant cause）。共 **6** 类；定义与判定规则见 §4，分布见 §5。

一题可同时具有多种 entanglement；标注字段 `primary` 只选其中主导的一项。Agent **看不见**该字段；仅用于选题平衡与分析切片，不进入 Functional 评分。

### 3.3 Lift Type

| Lift | 含义 |
| --- | --- |
| **Direct** | 与上游 API 基本同构，主要是抽取与解耦 |
| **Adapted** | 以上游主体功能为主，需接口/语义适配 |
| **Composite** | 无单一上游 API 可直接对应，需组合或多组件重建 |

定义详见 `docs/reference/LIFT_TAXONOMY.md`；分布见 §5。

## 4. Primary Entanglement Taxonomy

### 4.1 Definition

**Entanglement** 描述目标功能为什么不能只拿走其表面实现代码，而必须同时恢复仓库中的其他依赖、状态、配置或资源才能保持可观察行为。

> Entanglement characterizes why the implementation of a target feature cannot be cleanly separated from the surrounding repository while preserving its observable behavior.

示意：表面上只要 `parser.py` 中的 `parse()`，真正跑通还可能需要 Token/AST 数据模型、parser state、grammar registry、defaults 资源等——即存在 entanglement。

相对 feature location（定位实现代码），feature lifting 还要求把功能**完整分离**为独立可安装模块；entanglement 刻画的是 lifting 难点。

本分类是面向 feature lifting 的 **operational / empirical taxonomy**（metadata 字段名仍可能带历史后缀 `_coupling`；叙事统一用 entanglement）。

### 4.2 Six Categories

| Primary Entanglement | Metadata id（历史命名） | Operational definition |
| --- | --- | --- |
| **Data-model** | `data_model_coupling` | 功能行为依赖仓库特定的数据类、schema、对象不变量或类型关系 |
| **Parser-state** | `parser_state_coupling` | 功能依赖 lexer/parser 的 cursor、stack、grammar state、token stream 等隐式状态 |
| **Framework** | `framework_coupling` | 功能依赖 decorator、hook、registry、metaclass、plugin lifecycle 等框架机制 |
| **Config/environment** | `config_environment_coupling` | 功能行为受环境变量、配置文件、默认配置、runtime discovery 等影响 |
| **Resource** | `resource_coupling` | 功能依赖代码外资源（模板、schema、metadata、data file）或特定路径布局 |
| **Third-party dependency** | `third_party_dependency_coupling` | 核心行为依赖外部库；抽取时必须保留、适配或重建与该依赖的交互 |

### 4.3 Primary-label Decision Rule

一题可同时具有多种 entanglement（`entanglement.types` 可多选）。

**Primary** 判定：

> 当多个机制同时存在时，`primary` 指在任务设计与题级证据中，被判定为对目标功能**核心行为闭包形成主要约束**的机制；判断主要依据其缺失是否直接导致核心 behavioral contract 失败。若多个机制均满足该条件，则依据 annotation rubric 进行主导项判定，并记录其它机制于 `entanglement.types`。

`primary` 表示 dominant cause，**不**表示其它机制不存在，也**不**声称存在数学上唯一的 primary。Primary entanglement ≠ 难度等级。

### 4.4 Taxonomy Derivation and Annotation Status

该 taxonomy 参考 program slicing、separation of concerns、feature location 与 SE taxonomy construction 文献，并结合 benchmark construction 中的 empirical coding 归纳形成。

核心引用：

1. Weiser, TSE 1984 — Program Slicing  
2. Tarr et al., ICSE 1999 — Multi-dimensional separation of concerns  
3. Dit et al., JSEP 2013 — Feature location in source code: a taxonomy and survey  
4. Usman et al., IST 2017 — Taxonomies in software engineering（systematic mapping / development method）

补充：Ferrante et al., TOPLAS 1987 — Program Dependence Graph（data/control dependence 技术背景）。

归纳与使用顺序（先派生、后用于平衡，避免循环叙事）：

```text
initial Python-150 task inspection
        ↓
open coding of separation-failure causes
        ↓
derive recurring mechanisms
        ↓
freeze annotation rubric
        ↓
annotate / audit Python-150
        ↓
use taxonomy as one axis for External-50 selection and balancing
        ↓
apply the same rubric to the final Python-200
```

题级字段（已有）：`entanglement.primary` / `types` / `signals` / `description`。

**标注局限：** 当前含维护者 / AI-assisted 流程；**尚未**报告双人独立标注的 Cohen's κ / Krippendorff's α。在完成可靠性研究前，不得将该 taxonomy 表述为独立 human gold。下一步优先补齐 annotation rubric 与双人标注 κ。

## Appendix. Paper Notes（写作备注，非题集正文）

以下内容仅供论文措辞，不进入组会「题集构成」主叙述。

- **命名：** 论文中用 *Primary Entanglement Mechanism* / *Entanglement Type*，避免 *Coupling Type*，以免与 Constantine 经典 coupling 或 PDG 的 data/control dependence 混淆。  
- **定位句：** 六类是 feature lifting 的 empirical taxonomy，不声称是通用软件耦合公理；可表述为 *a taxonomy of feature-level entanglement mechanisms in real-world repositories*。  
- **证据加强（可选）：** 题级补 `evidence: {artifact, dependency, failure_without_it}`；抽 50–100 题双人独立标注并报告 κ。  
- **Related work 展开：** Weiser（slicing / 行为保持分解）、Tarr（concern 分离困难）、Dit（location → lifting）、Usman（taxonomy 构建方法）；Ferrante 作 PDG / dependence 补充。细节放 related work，勿堆在题集构成表里。
